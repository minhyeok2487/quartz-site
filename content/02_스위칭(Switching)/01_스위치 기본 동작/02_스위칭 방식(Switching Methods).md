# 1. 스위치는 프레임을 어떻게 처리할까?

앞 장에서 스위치의 역할과 핵심 기능(Learning, Forwarding, Filtering, Flooding)을 배웠습니다. 스위치가 MAC 주소를 학습하고, 목적지 포트로 프레임을 전달한다는 것을 알았죠.

그런데 한 가지 의문이 생깁니다. 스위치가 프레임을 받았을 때, **언제** 전달을 시작할까요?

- 프레임 전체를 다 받고 나서 보낼까요?
- 아니면 목적지 주소만 확인하고 바로 보낼까요?

이 질문에 대한 답이 바로 **스위칭 방식(Switching Method)** 입니다.

## 왜 스위칭 방식이 중요할까?

스위칭 방식에 따라 두 가지가 달라집니다.

**첫째, 지연 시간(Latency)** 입니다. 프레임이 스위치에 들어와서 나갈 때까지 걸리는 시간이 달라집니다. 실시간 통신(VoIP, 화상회의)에서는 이 지연이 매우 중요합니다.

**둘째, 오류 처리**입니다. 손상된 프레임을 걸러낼 수 있느냐 없느냐가 달라집니다. 오류가 많은 네트워크에서는 이것이 중요해집니다.

# 2. Store-and-Forward 방식

## 동작 원리

Store-and-Forward는 이름 그대로 **"저장한 다음 전달"** 하는 방식입니다.

```
프레임 수신 시작
       │
       ▼
┌─────────────────┐
│  전체 프레임을   │
│  버퍼에 저장     │
└────────┬────────┘
         │
         ▼
┌─────────────────┐
│   FCS 검사      │ ← CRC 오류 확인
│  (오류 검증)    │
└────────┬────────┘
         │
    ┌────┴────┐
    │ 오류?   │
    └────┬────┘
    Yes  │  No
    ▼    │
  폐기   ▼
      전달 시작
```

스위치가 프레임을 받으면:

1. **전체 프레임을 버퍼에 저장**합니다 (목적지 MAC, 출발지 MAC, 데이터, FCS 모두)
2. **FCS(Frame Check Sequence)를 검사**합니다 - CRC 계산으로 오류 확인
3. **오류가 있으면 폐기**, 없으면 목적지 포트로 전달

## FCS란?

FCS(Frame Check Sequence)는 프레임의 맨 끝에 붙는 4바이트 값입니다. 송신 측에서 프레임 내용을 기반으로 CRC(Cyclic Redundancy Check) 계산을 해서 붙여 보냅니다.

```
이더넷 프레임:
┌─────────┬─────────┬──────┬────────────┬─────┐
│목적지MAC│출발지MAC│ Type │    Data    │ FCS │
│ 6 bytes │ 6 bytes │2bytes│ 46-1500B   │4bytes│
└─────────┴─────────┴──────┴────────────┴─────┘
                                          ↑
                                    CRC 검사값
```

수신 측(스위치)은 받은 프레임으로 똑같이 CRC를 계산해서 FCS와 비교합니다. 값이 다르면? 전송 중에 데이터가 손상된 것입니다. 이런 프레임은 폐기합니다.

## Store-and-Forward의 장단점

**장점:**
- 손상된 프레임을 걸러냄 (오류 전파 방지)
- Runt 프레임(64바이트 미만)과 Giant 프레임(1518바이트 초과) 필터링
- QoS 적용 가능 - 전체 프레임을 봐야 우선순위 판단 가능

> **QoS(Quality of Service)란?**
> 네트워크에서 특정 트래픽에 우선순위를 부여하는 기술입니다. 예를 들어, 음성 통화(VoIP)는 끊김 없이 전달되어야 하므로 일반 파일 다운로드보다 높은 우선순위를 받습니다. 스위치가 QoS를 적용하려면 프레임 내부의 우선순위 정보를 확인해야 하는데, 이를 위해서는 프레임 전체를 받아야 합니다.

**단점:**
- 지연 시간이 상대적으로 김
- 프레임 크기에 따라 지연이 달라짐 (큰 프레임일수록 오래 걸림)

## 지연 시간 계산

1500바이트 프레임을 100Mbps 링크에서 받는다면:

```
수신 시간 = 프레임 크기 / 링크 속도
         = (1500 × 8 bits) / 100,000,000 bps
         = 12,000 / 100,000,000
         = 0.00012초 = 120μs (마이크로초)
```

Store-and-Forward에서는 이 120μs를 기다린 후에야 전달을 시작합니다.

# 3. Cut-Through 방식

## 동작 원리

Cut-Through는 **"잘라서 통과"** 시키는 방식입니다. 프레임 전체를 기다리지 않습니다.

```
프레임 수신 시작
       │
       ▼
┌─────────────────┐
│  목적지 MAC만   │ ← 처음 6바이트만 확인
│     확인        │
└────────┬────────┘
         │
         ▼
    즉시 전달 시작! ← 나머지는 받으면서 동시에 전송
```

스위치가 프레임의 **처음 6바이트(목적지 MAC 주소)** 만 읽으면 바로 전달을 시작합니다. 프레임의 나머지 부분은 받으면서 동시에 내보냅니다.

## Cut-Through의 장단점

**장점:**
- 지연 시간이 매우 짧음 (고정된 짧은 지연)
- 프레임 크기와 관계없이 일정한 지연
- 고속 네트워크에서 성능 향상

**단점:**
- 오류 검사를 하지 않음 - 손상된 프레임도 그대로 전달
- Runt, Giant 프레임도 전달됨
- QoS 적용 어려움

## 지연 시간 비교

같은 1500바이트 프레임, 100Mbps 링크에서:

| 방식 | 확인하는 부분 | 지연 시간 |
|------|--------------|----------|
| Store-and-Forward | 전체 1500+ 바이트 | ~120μs |
| Cut-Through | 처음 6바이트 | ~5μs |

Cut-Through가 약 **20배 이상 빠릅니다**.

# 4. Fragment-Free 방식

## 동작 원리

Fragment-Free는 Store-and-Forward와 Cut-Through의 **절충안**입니다.

```
프레임 수신 시작
       │
       ▼
┌─────────────────┐
│  처음 64바이트  │ ← 충돌 윈도우만 확인
│     확인        │
└────────┬────────┘
         │
         ▼
    전달 시작
```

**처음 64바이트**만 확인하고 전달을 시작합니다. 왜 하필 64바이트일까요?

## 64바이트의 의미 - 충돌 윈도우

이더넷에서 충돌(Collision)이 발생하면, 충돌 신호가 송신 측까지 돌아오는 데 시간이 걸립니다. 이 시간 동안 최소한 전송되어야 하는 데이터 크기가 **64바이트**입니다.

```
충돌 발생 시나리오:
┌────┐                           ┌────┐
│PC-A│ ─────────────────────────→│PC-B│
└────┘         충돌!              └────┘
        ←─────────────────────────
         충돌 신호가 돌아옴

이더넷 최대 거리에서 신호 왕복 시간 동안
전송되는 최소 프레임 크기 = 64바이트
```

**64바이트 미만의 프레임(Runt Frame)** 은 대부분 충돌로 인해 손상된 프레임입니다. Fragment-Free는 이런 Runt 프레임을 걸러냅니다.

## Fragment-Free의 장단점

**장점:**
- Cut-Through보다 안전 (Runt 프레임 필터링)
- Store-and-Forward보다 빠름
- 충돌로 인한 오류 대부분 제거

**단점:**
- 64바이트 이후의 오류는 감지 못함
- Store-and-Forward만큼 완벽한 오류 검사는 아님

# 5. 세 가지 방식 비교

## 한눈에 보는 비교표

| 특성 | Store-and-Forward | Cut-Through | Fragment-Free |
|------|-------------------|-------------|---------------|
| **확인 범위** | 전체 프레임 | 6바이트 (목적지 MAC) | 64바이트 |
| **FCS 검사** | O | X | X |
| **Runt 필터링** | O | X | O |
| **Giant 필터링** | O | X | X |
| **지연 시간** | 가변 (프레임 크기에 비례) | 고정 (매우 짧음) | 고정 (짧음) |
| **오류 전파** | 방지 | 전파됨 | 일부 방지 |
| **QoS 지원** | O | X | X |

## 시각적 비교

```
프레임: [목적지MAC][출발지MAC][Type][      Data      ][FCS]
        |←─ 6B ──→|←─ 6B ──→|← 2B→|←─ 46~1500B ───→|←4B→|

Cut-Through:     ▲
                 │ 여기서 전달 시작

Fragment-Free:                    ▲
                                  │ 64바이트 후 전달 시작

Store-and-Forward:                                      ▲
                                                        │ 전체 수신 후 전달
```

# 6. 실무에서의 선택

## 현대 스위치의 기본값

오늘날 대부분의 스위치는 **Store-and-Forward**를 기본으로 사용합니다.

왜 그럴까요?

1. **하드웨어 성능 향상**: 과거에는 Store-and-Forward의 지연이 문제였지만, 현대 스위치는 하드웨어 기반 처리로 지연이 미미함
2. **QoS 필요성**: VoIP, 화상회의 등 실시간 트래픽 우선순위 처리 필요
3. **안정성 중시**: 오류 프레임 전파 방지가 더 중요해짐

## 언제 어떤 방식을 쓸까?

**Store-and-Forward가 적합한 경우:**
- Access 계층 (사용자 단말 연결 지점)
- QoS가 필요한 환경
- 오류가 자주 발생하는 네트워크

**Cut-Through가 적합한 경우:**
- Core/Distribution 계층 (백본)
- 초저지연이 필수인 환경 (고빈도 거래, HPC)
- 오류 발생이 적은 안정된 네트워크

**Fragment-Free는?**
- 현재는 거의 사용되지 않음
- Cut-Through와 Store-and-Forward 사이의 과도기적 기술

## Cisco 스위치의 경우

Cisco Catalyst 스위치 대부분은 Store-and-Forward만 지원합니다. Nexus 시리즈 같은 데이터센터용 스위치에서 Cut-Through 옵션을 제공하기도 합니다.

# 7. Adaptive Switching (적응형 스위칭)

일부 스위치는 **상황에 따라 자동으로 방식을 전환**합니다.

```
평상시: Cut-Through (빠른 전달)
         │
         ▼
    오류율 증가 감지
         │
         ▼
자동 전환: Store-and-Forward (오류 필터링)
         │
         ▼
    오류율 감소 감지
         │
         ▼
다시 전환: Cut-Through (빠른 전달)
```

관리자가 오류 임계값을 설정하면:
- 오류율이 임계값을 넘으면 → Store-and-Forward로 전환
- 오류율이 정상으로 돌아오면 → Cut-Through로 복귀

이렇게 속도와 안정성의 균형을 자동으로 맞춥니다.

# 8. 정리하며

스위칭 방식은 스위치가 프레임을 언제 전달하기 시작하느냐를 결정합니다.

**핵심 포인트:**

**Store-and-Forward**는 전체 프레임을 받고 FCS 검사 후 전달합니다. 안전하지만 지연이 있고, 현대 스위치의 기본 방식입니다.

**Cut-Through**는 목적지 MAC(6바이트)만 보고 즉시 전달합니다. 빠르지만 오류 검사가 없고, 초저지연 환경에서 사용됩니다.

**Fragment-Free**는 64바이트 확인 후 전달합니다. 두 방식의 절충안이며, Runt 프레임을 필터링할 수 있습니다.

**실무에서는** 대부분 Store-and-Forward를 사용합니다. 현대 하드웨어는 충분히 빠르고, QoS와 안정성이 더 중요하기 때문입니다.
