# Cisco IOS 접근 제어 정리

GNS3 실습 환경(IOS 15.7) 및 실무 장비 컨피그 분석을 기반으로 Cisco 라우터/스위치의 패스워드, 인증, 접근 제어 설정을 정리한 문서입니다.

## 1. service password-encryption

라우터 초기 상태에서는 `no service password-encryption`으로 되어 있다. 활성화 방법:

```
Router(config)# service password-encryption
```

이 명령어를 켜면 running-config에 평문으로 저장된 패스워드들이 **Type 7** 암호화로 변환된다. 단, Type 7은 보안 강도가 매우 약하며 온라인 디코더로 쉽게 복호화가 가능하다.

## 2. 패스워드 Type 비교

|Type|알고리즘|방향|강도|
|---|---|---|---|
|0|평문|-|❌|
|7|Vigenère|양방향 (복호화 가능)|매우 약함|
|5|MD5|단방향 (복구 불가)|보통|
|8|PBKDF2-SHA256|단방향|강함|
|9|scrypt|단방향|매우 강함|

### Type 7 (password 키워드)

`service password-encryption`에 의존하며, 양방향 암호화라 원문 복구가 가능하다.

### Type 5 (secret 키워드)

`service password-encryption` 설정 여부와 관계없이 자체적으로 MD5 해시 처리된다. `secret` 키워드를 사용하면 자동으로 Type 5가 적용된다.

```
Router(config)# enable secret MyPassword
Router(config)# username admin secret MyPassword
```

### Type 8, 9 (최신 IOS)

```
Router(config)# username admin algorithm-type scrypt secret MyPassword
```

IOS 버전에 따라 지원 여부가 다르다.

### secret 키워드를 사용할 수 있는 곳

`secret` 키워드는 아무 곳에서나 쓸 수 있는 것이 아니다. 사용 가능한 곳은 다음 두 곳뿐이다.

- `enable secret` — enable 모드 진입용
- `username ... secret` — 로컬 계정용

line 모드(`line con`, `line vty`, `line aux`)에서는 `secret`을 지원하지 않고 `password`만 사용 가능하다. 따라서 line에 직접 패스워드를 거는 방식은 Type 7까지만 가능하며, 이것이 `login local`로 계정 기반 인증을 권장하는 이유 중 하나이다.

### 핵심 정리

- `password` 키워드 → `service password-encryption`에 의존 (Type 7)
- `secret` 키워드 → 자체 해시 처리 (Type 5 이상), `service password-encryption` 불필요
- line 모드에서는 `secret` 사용 불가 → `login local`로 계정 기반 인증을 사용해야 Type 5 이상 적용 가능

## 3. GPU를 이용한 오프라인 패스워드 크래킹

### 오프라인 공격이란?

`show running-config`의 해시값이 유출되면(백업 파일 탈취, 관리자 PC 해킹 등), 공격자는 장비에 접속할 필요 없이 자기 컴퓨터에서 Hashcat 같은 도구로 해시를 크래킹할 수 있다. 장비를 거치지 않으므로 로그인 딜레이도, 실패 횟수 제한도 없다.

```
"cisco123" → MD5 해시 → $1$pwa5$7tpITLeqUOHI.y8haBDdf0 → 일치! → 뚫림
```

### RTX 5080 벤치마크 (Hashcat 6.2.6)

RTX 5080 한 장으로 Cisco-IOS `$1$`(Type 5, MD5) 기준 **초당 약 4,280만 개**의 해시를 시도할 수 있다.

|패스워드 조건|조합 수|크래킹 예상 시간|
|---|---|---|
|숫자 6자리|100만 개|**0.02초**|
|영소문자 6자리|약 3억 개|**약 7초**|
|영대소문자+숫자 8자리|약 2,180억 개|**약 1.4시간**|
|영대소문자+숫자+특수 10자리|약 60경 개|**수백 년**|

`cisco123` 같은 단순한 패스워드는 사전 공격으로 1초도 걸리지 않는다.

### 알고리즘별 크래킹 저항력

같은 RTX 5080에서 순수 MD5는 초당 1,030억 개, NTLM은 초당 1,566억 개를 처리한다. Cisco IOS의 `$1$`가 이보다 느린 이유는 내부적으로 MD5를 1,000번 반복하기 때문이다. 그럼에도 짧거나 단순한 패스워드는 순식간에 뚫리므로, scrypt(Type 9)를 사용하거나 패스워드 자체를 12자리 이상으로 길고 복잡하게 설정하는 것이 중요하다.

### 대응 방안

- 컨피그 전송 시 TFTP 대신 SCP 사용
- 백업 파일 접근 권한 제한
- `algorithm-type scrypt` 사용 (Type 9)
- 12자리 이상, 영대소문자+숫자+특수문자 조합

## 4. 콘솔 접속과 인증

### 왜 초기 상태에서 인증 없이 들어가는가?

공장 출하 상태에서는 콘솔에 인증이 설정되어 있지 않다. 새 장비를 처음 셋업할 때 인증이 걸려 있으면 아예 접속을 못 하기 때문에 의도된 설계이다.

### login 동작 방식 (세 가지, 상호 배타적)

|설정|동작|
|---|---|
|`no login` (또는 login 미설정)|인증 없이 바로 진입|
|`login`|`password` 명령어로 설정한 패스워드만 물어봄 (username 없음)|
|`login local`|로컬 DB(`username ... secret ...`)로 인증 (username + password)|

세 가지 중 하나만 적용되므로, `login local`이 설정된 상태에서는 같은 라인의 `password` 명령어가 무시된다.

## 5. line con 0 설정 상세

```
line con 0
 exec-timeout 0 0
 privilege level 15
 password cisco123
 logging synchronous
 login local
```

|명령어|설명|
|---|---|
|`exec-timeout 0 0`|자동 로그아웃 비활성화. 기본값은 10분. 실습용으로 편리하지만 실무에서는 보안상 비권장|
|`privilege level 15`|로그인 시 바로 Privileged EXEC 모드(#) 진입. `enable` 입력 불필요|
|`password cisco123`|`login local`이 있으면 무시됨. 습관적으로 남겨둔 설정|
|`logging synchronous`|syslog 메시지가 입력 중인 명령어를 밀어내지 않도록 깔끔하게 재출력|
|`login local`|로컬 계정(username/secret)으로 인증|

## 6. enable secret vs username secret

이 두 가지는 완전히 별개의 인증이다.

|구분|용도|설정 명령어|
|---|---|---|
|`username ... secret`|장비 로그인용 (콘솔, VTY 등)|`username admin secret Pass1`|
|`enable secret`|User → Privileged EXEC 모드 전환용|`enable secret Pass2`|

같은 패스워드 문자열을 넣어도 MD5 솔트(salt)가 랜덤 생성되므로 해시값은 서로 다르게 보인다. 보안상 서로 다른 패스워드로 설정하는 것이 올바르다.

### 로컬 계정이 여러 개여도 enable secret은 하나

로컬 사용자 계정은 여러 개 만들 수 있지만, `enable secret`은 장비에 **하나만** 존재한다.

```
username admin secret Pass1
username operator secret Pass2
username nocuser secret Pass3

enable secret EnablePass       ← 딱 하나, 모든 사용자가 동일한 패스워드 입력
```

누가 로그인했든 `enable`을 치면 같은 패스워드를 물어본다. 이로 인해 enable 패스워드를 여러 사용자가 공유하게 되어 누가 무엇을 했는지 추적이 어려워지는 문제가 있다. 이를 해결하는 방법은 두 가지다.

**방법 1: privilege level로 분리**

```
username admin privilege 15 secret Pass1      ← 로그인 시 바로 #모드, enable 불필요
username operator privilege 1 secret Pass2     ← User 모드만 사용 가능
```

**방법 2: TACACS+로 사용자별 권한 제어**

AAA를 사용하면 ISE에서 사용자마다 다른 privilege level을 부여할 수 있고, 누가 언제 enable 모드에 들어갔는지 로그도 남길 수 있다. 결국 실무에서는 TACACS+를 사용하게 되는 이유이기도 하다.

## 7. Privilege Level

0부터 15까지 총 16단계가 존재한다.

|레벨|의미|
|---|---|
|**0**|최소 권한. `logout`, `enable`, `disable` 정도만 가능|
|**1**|기본 User EXEC 모드(>). 일부 `show` 명령어 사용 가능|
|**2~14**|커스텀 레벨. 관리자가 특정 명령어를 할당 가능|
|**15**|최고 권한. Privileged EXEC 모드(#). 모든 명령어 사용 가능|

### 커스텀 레벨 예시

```
Router(config)# privilege exec level 7 show running-config
Router(config)# username operator privilege 7 secret OpPass123
```

실무에서는 중간 레벨을 세밀하게 나누기보다 TACACS+를 통한 Role-Based Access Control을 사용하는 것이 일반적이다.

## 8. 콘솔 포트 종류 (RJ-45 vs USB)

최근 Cisco 장비는 RJ-45 콘솔 포트 외에 USB Mini-B(또는 Micro-B) 콘솔 포트도 함께 제공한다. 둘 다 논리적으로는 **같은 `line con 0`**이며, 물리적 포트만 다를 뿐이다.

두 포트를 동시에 연결하면 **USB 쪽이 우선순위**를 가진다. USB 콘솔이 연결되면 RJ-45 콘솔은 비활성화되고, USB를 빼면 다시 RJ-45로 전환된다.

```
Router(config)# line con 0
Router(config-line)# media-type rj45    ← RJ-45 강제 사용
```

USB 콘솔을 사용하려면 PC에 Cisco USB 콘솔 드라이버를 설치해야 한다. 드라이버 인식 문제가 가끔 발생하므로, 실무에서는 RJ-45 콘솔 + USB-시리얼 어댑터 조합을 많이 사용한다.

## 9. Line 종류

### 왜 `line con 0`인가?

콘솔 포트는 물리적으로 하나밖에 없어서 항상 0번이다. `line con 1`을 입력하면 에러가 발생한다. 그런데 굳이 번호를 붙이는 이유는 IOS의 line 명령어 문법이 모든 라인 타입에 대해 통일된 구조(`line [타입] [시작번호] [끝번호]`)로 설계되어 있기 때문이다.

```
line con 0        ← 콘솔은 항상 0번 하나
line vty 0 4      ← vty는 범위 지정 가능 (0~4번, 5개 라인)
line vty 5 15     ← 별도 범위로 다른 설정 적용 가능
line tty 1 16     ← 액세스 서버의 시리얼 포트 1~16번
```

콘솔은 항상 하나뿐이지만 문법 일관성을 위해 번호를 요구하므로, `line con 0`이 사실상 고정 표현이다.

### Line 종류 요약

`line ?` 명령어로 확인할 수 있는 라인 종류는 다음과 같다.

|Line|설명|실무 사용 빈도|
|---|---|---|
|**console** (line con 0)|물리적 콘솔 포트. 장비에 직접 케이블 연결해서 접속. 항상 0번 하나|★★★|
|**vty** (line vty 0 4)|Virtual Terminal. SSH/Telnet 원격 접속 세션 담당. 기본 5개(0~4), `line vty 0 15`로 확장 시 최대 16개 동시 세션 가능|★★★|
|**aux** (line aux 0)|Auxiliary 포트. 모뎀 연결을 통한 다이얼인 원격 접속 용도. 요즘은 거의 사용하지 않으며 보안상 비활성화 권장|★|
|**tty**|물리적 시리얼 포트(비동기 포트)에 연결된 터미널 라인. 액세스 서버에서 여러 장비를 시리얼로 관리할 때 사용. 일반 라우터에서는 거의 사용하지 않음|★|
|**x/y** (Slot/Port)|모듈형 라우터에서 모뎀 카드(예: WIC-1AM)가 장착된 슬롯/포트 지정. 요즘은 거의 사용하지 않음|★|
|**<0-582>**|모든 라인을 절대 번호(absolute line number)로 직접 지정하는 방식. `show line` 명령어로 각 라인 번호를 확인 가능|-|

실무에서 실제로 사용하는 것은 **console과 vty** 두 가지가 대부분이며, aux는 보안상 막아두고 나머지는 특수 환경이 아니면 사용할 일이 거의 없다.

### 사용하지 않는 Line 비활성화

Line은 IOS에 내장된 것이라 `no line aux 0` 같은 명령어로 삭제할 수 없다. 대신 비활성화하는 방식으로 막아야 한다.

```
Router(config)# line aux 0
Router(config-line)# no exec              ← EXEC 세션 자체 비활성화
Router(config-line)# transport input none  ← 어떤 프로토콜로도 접속 불가
Router(config-line)# login local           ← 혹시 모를 상황 대비 인증 요구
Router(config-line)# exec-timeout 0 1      ← 세션이 생기더라도 1초 후 자동 종료
```

`no exec` 하나만으로도 충분하지만, 보안 감사에서는 겹겹이 막아두는 것을 권장한다. 사용하지 않는 vty 라인도 같은 방식으로 비활성화하는 것이 좋다.

### Line 설정 시 자주 사용하는 명령어

|명령어|설명|
|---|---|
|`exec-timeout`|세션 타임아웃 설정. 실무 필수|
|`login` / `login local`|인증 방식 설정|
|`transport input`|허용할 프로토콜 지정 (ssh, telnet, none 등)|
|`logging synchronous`|로그 메시지가 입력 중인 명령어를 밀어내지 않도록 재출력|
|`access-class`|ACL 기반 접속 제한. 특정 IP만 허용할 때 사용|
|`privilege level`|접속 시 기본 권한 레벨 지정|
|`no exec`|EXEC 세션 비활성화. 사용하지 않는 라인 차단|
|`length`|터미널 화면 줄 수 설정. `length 0`이면 --More-- 없이 전체 출력|
|`history size`|명령어 히스토리 버퍼 크기 설정. 기본 10개|
|`session-timeout`|다른 장비로 연결한 세션의 타임아웃 (exec-timeout과 별개)|
|`absolute-timeout`|입력 여부와 무관하게 무조건 지정 시간 후 종료|
|`autocommand`|로그인 시 특정 명령어 자동 실행|

### 실무 시나리오별 설정 예시

**시나리오 1: 보안 감사 대비 — VTY에 SSH만 허용하고 특정 관리 대역만 접속 가능하게**

관리자가 보안 팀으로부터 "원격 접속은 SSH만 허용하고, 관리 VLAN(10.10.10.0/24)에서만 접속 가능하게 하라"는 요구를 받은 경우.

```
ip access-list standard VTY-ACCESS
 permit 10.10.10.0 0.0.0.255
 deny any

line vty 0 4
 transport input ssh
 access-class VTY-ACCESS in
 login local
 exec-timeout 5 0
line vty 5 15
 transport input none
 no exec
```

핵심: `transport input ssh`로 Telnet 차단, `access-class`로 IP 제한, 사용하지 않는 vty 5~15는 완전 비활성화.

**시나리오 2: NOC 모니터링 전용 계정 — 읽기 권한만 부여하고 설정 변경 불가하게**

NOC(Network Operations Center) 직원이 장비 상태만 확인할 수 있도록 제한된 계정을 만들어달라는 요구를 받은 경우.

```
username nocuser privilege 1 secret NocPass123

privilege exec level 1 show running-config
privilege exec level 1 show ip interface brief
privilege exec level 1 show ip route

line vty 0 4
 transport input ssh
 login local
 exec-timeout 10 0
 length 0
```

핵심: `privilege 1`로 User EXEC 모드만 허용. `enable` 비밀번호를 모르면 # 모드 진입 불가. `length 0`으로 show 명령어 출력 시 --More-- 없이 한눈에 확인 가능.

**시나리오 3: 현장 장비 초기 셋업 — 콘솔에서 안전하게 작업할 수 있는 환경 구성**

신규 장비를 데이터센터에서 콘솔로 초기 설정하는데, 작업 중 세션이 끊기지 않도록 하고 로그 메시지에 방해받지 않도록 설정.

```
line con 0
 exec-timeout 0 0
 logging synchronous
 history size 256
 login local
```

핵심: `exec-timeout 0 0`으로 타임아웃 비활성화(초기 셋업 중 세션 유지), `logging synchronous`로 작업 편의성 확보, `history size 256`으로 이전 명령어 빠르게 재사용. 초기 셋업 완료 후 반드시 `exec-timeout`을 적절한 값으로 변경해야 한다.

## 11. 실무 트러블슈팅 사례

접근 제어 설정과 관련하여 실제로 발생하는 대표적인 트러블슈팅 사례를 정리한다.

### 사례 1: AAA 설정 후 TACACS+ 서버 장애로 전체 락아웃

AAA를 켜고 TACACS+ 서버만 인증 방법으로 설정했는데, 서버와의 통신이 끊기면 아무도 장비에 접속할 수 없게 된다.

```
! 위험한 설정 (폴백 없음)
aaa authentication login default group tacacs+

! 안전한 설정 (local 폴백 포함)
aaa authentication login default group tacacs+ local
```

Cisco 커뮤니티에서 한 관리자가 TACACS+와 RADIUS를 혼합 설정하면서 장비에서 완전히 잠기는 사고가 보고되었다. 해결책은 TACACS+ 서버를 해당 라우터에서 도달 불가능하게 만들어(null route나 ACL로 차단) 폴백 인증이 작동하게 하는 것이었다.

**교훈:** `aaa authentication` 설정 시 반드시 `local`을 폴백으로 넣고, 로컬 비상 계정을 만들어둬야 한다.

> 출처: Cisco Community — "Locked out of router with TACACS" https://community.cisco.com/t5/policy-and-access/locked-out-of-router-with-tacacs/td-p/2787001

### 사례 2: `aaa new-model` 입력 순간 텔넷 세션 끊김

`aaa new-model` 명령어를 입력하는 순간, 콘솔을 제외한 모든 line과 인터페이스에 즉시 로컬 인증이 적용된다. 이 시점에 텔넷 세션이 열려 있으면 타임아웃되거나 재접속 시 인증을 요구하게 되는데, 아직 사용자 계정이나 인증 방법을 설정하지 않은 상태라 접속이 불가능해진다.

Cisco 공식 문서에서도 AAA 설정 전에 반드시 컨피그를 저장하고, 설정이 완료되어 정상 동작이 확인된 후에만 다시 저장하라고 권고한다. 문제가 생기면 reload로 이전 설정으로 롤백할 수 있도록 하기 위함이다.

**교훈:** AAA 설정은 반드시 콘솔에서 진행하고, 원격(SSH/Telnet)으로 하지 말 것.

> 출처: Cisco — "Configure Basic AAA on an Access Server" https://www.cisco.com/c/en/us/support/docs/security-vpn/terminal-access-controller-access-control-system-tacacs-/10384-security.html

### 사례 3: 패스워드 분실로 ROMMON 리커버리

Cisco 커뮤니티에서 한 관리자가 Cisco 4431 라우터의 콘솔 패스워드를 설정할 때 오타를 내고 저장하여, 이후 완전히 잠겨서 접속이 불가능해진 사례가 보고되었다. 패스워드 리커버리를 위해서는 반드시 콘솔 직접 연결이 필요하며, SSH나 Telnet으로는 리커버리가 불가능하다.

복구 절차:

```
1. 콘솔 연결 후 라우터 재부팅
2. 부팅 중 Ctrl+Break로 ROMMON 진입
3. confreg 0x2142        ← startup-config 무시 설정
4. reset                 ← 재부팅
5. 빈 설정으로 부팅 후 copy startup-config running-config으로 기존 설정 복원
6. 패스워드 변경 후 config-register 0x2102로 원복
7. write memory로 저장
```

단, `no service password-recovery`가 설정되어 있으면 이 절차가 불가능하며, 시도 시 전체 설정이 초기화된다.

**교훈:** 패스워드 변경 시 반드시 검증 후 저장하고, 비상 계정을 별도로 유지할 것.

> 출처: Cisco Community — "Bypass or reset console password" https://community.cisco.com/t5/network-management/bypass-or-reset-console-password/td-p/3316309
> 
> 출처: Cisco — "Troubleshoot Password Recovery in IOS and IOS XE Routers" https://www.cisco.com/c/en/us/support/docs/ios-nx-os-software/ios-xe-16/217045-troubleshoot-password-recovery-in-cisco.html

## 13. VTY access-class ACL 설정 가이드

VTY 라인에 ACL을 적용하면 특정 IP에서만 원격 접속을 허용할 수 있다. 접근 제어에서 가장 기본적이면서도 효과가 큰 설정이다.

### 기본 구성 (Standard ACL)

```
ip access-list standard VTY-ACCESS
 permit 10.10.10.0 0.0.0.255       ← 관리 대역
 permit host 192.168.250.100       ← 특정 관리 서버
 deny any log                      ← 나머지 차단 + 로깅

line vty 0 4
 access-class VTY-ACCESS in
line vty 5 15
 access-class VTY-ACCESS in
```

Standard ACL은 출발지 IP만 제어한다. 대부분의 VTY 접근 제한에는 이것으로 충분하다.

### 심화 구성 (Extended ACL)

Extended ACL을 사용하면 프로토콜 레벨까지 제어할 수 있다. 예를 들어 특정 IP는 SSH만, 다른 IP는 SSH와 SNMP 모두 허용하는 식의 세밀한 제어가 가능하다.

```
ip access-list extended VTY_ACL
 permit ip host 10.146.49.8 any        ← 관리 서버
 permit ip host 10.146.49.9 any        ← ISE 서버
 permit ip 10.200.0.0 0.0.0.255 any    ← NOC 대역
 deny   ip any any log                 ← 나머지 차단 + 로깅

line vty 0 15
 access-class VTY_ACL in
```

### 주의사항

- **반드시 모든 VTY 라인(0~4, 5~15)에 동일한 ACL을 적용**해야 한다. 일부만 적용하면 ACL이 없는 라인으로 우회 접속이 가능하다.
- ACL 적용 전 **자신의 접속 IP가 permit에 포함되어 있는지 반드시 확인**한다. 실수로 자신의 IP를 빠뜨리면 원격 접속이 차단된다.
- ACL 변경 시 **콘솔 세션을 열어둔 상태**에서 작업하는 것이 안전하다.
- `deny any log`를 마지막에 넣으면 차단된 접속 시도가 로그에 남아 보안 모니터링에 유용하다.

## 14. AAA 메서드 리스트 (default vs named)

AAA에서 인증 방법을 정의할 때 **default 리스트**와 **named 리스트** 두 가지 방식이 있다. 이 차이를 이해하지 못하면 의도치 않은 인증 동작이나 락아웃이 발생할 수 있다.

### default 메서드 리스트

```
aaa authentication login default group tacacs+ local
```

`default`로 정의하면 **명시적으로 다른 리스트를 지정하지 않은 모든 line에 자동 적용**된다. 별도 설정 없이 모든 VTY, 콘솔에 일괄 적용되어 편리하지만, 콘솔까지 TACACS+를 타게 되어 서버 장애 시 비상 접근이 어려울 수 있다.

### named 메서드 리스트

```
aaa authentication login CORP group CORP local
aaa authentication login console none
```

이름을 지정하면 **line에서 명시적으로 적용해야만 동작**한다.

```
line con 0
 login authentication console       ← console 리스트 적용 (인증 없음)

line vty 0 15
 login authentication CORP           ← CORP 리스트 적용 (TACACS+ → local)
```

### 왜 named 리스트를 쓰는가?

핵심은 **콘솔과 VTY의 인증 정책을 분리**할 수 있다는 것이다.

|방식|콘솔|VTY|장점|단점|
|---|---|---|---|---|
|default만 사용|TACACS+ → local|TACACS+ → local|설정 간단|콘솔도 TACACS+ 의존|
|named 분리|none (인증 없음)|TACACS+ → local|비상 접근 경로 확보|물리 보안 필요|

엔터프라이즈 환경에서는 named 리스트로 콘솔을 `none`으로 설정하되, 데이터센터 물리적 출입 통제로 보안을 보완하는 것이 일반적이다. 이 방식을 사용하면 TACACS+ 서버가 전부 장애가 나도 콘솔을 통한 비상 접근이 가능하다.

### 메서드 리스트 폴백 동작

```
aaa authentication login default group tacacs+ local
```

위 설정에서 폴백이 발생하는 조건을 정확히 이해해야 한다.

- TACACS+ 서버가 **응답 없음(ERROR)** → `local`로 폴백 ✅
- TACACS+ 서버가 **인증 거부(FAIL)** → 폴백 안 함, 인증 실패 ❌

즉 서버가 "이 사용자 없음"이라고 명시적으로 거부하면 local로 넘어가지 않는다. 서버와 아예 통신이 안 될 때만 폴백이 작동한다. 이 동작 차이를 모르면 "로컬 계정을 만들어뒀는데 왜 안 되지?"라는 상황이 발생할 수 있다.

### AAA Accounting (심화)

인증(Authentication)과 권한(Authorization) 외에 **기록(Accounting)**도 중요하다.

```
aaa accounting exec CORP start-stop group CORP
aaa accounting commands 1 CORP start-stop group CORP
aaa accounting commands 15 CORP start-stop group CORP
```

- **exec accounting** — 누가 언제 로그인/로그아웃했는지 기록
- **commands accounting** — 어떤 명령어를 실행했는지 기록

보안 감사에서 "누가 언제 `write erase`를 쳤는가?"를 추적할 수 있으려면 이 설정이 필수다.

## 15. Banner 설정 (motd / login / exec)

Cisco 장비에서 설정할 수 있는 배너는 3종류이며, **표시 순서**가 정해져 있다.

### 표시 순서

```
1. banner motd     ← 접속 시 가장 먼저 표시
2. banner login    ← 로그인 프롬프트 직전에 표시
3. (사용자 인증)
4. banner exec     ← 인증 성공 후 EXEC 세션 시작 시 표시
```

### 각 배너의 용도

**banner motd (Message of the Day)**

모든 접속에 대해 가장 먼저 보여주는 메시지. 일반적으로 법적 경고문(Legal Notice)을 넣는다.

```
banner motd ^C
############################################################
#         !!! Authorized Access Only !!!                   #
#  This is a private computer facility.                    #
#  Unauthorized access is prohibited.                      #
############################################################
^C
```

**banner login**

로그인 프롬프트 직전에 표시. 인증 전 사용자에게 보여줄 추가 안내.

**banner exec**

인증 성공 후 EXEC 세션이 시작될 때 표시. 인증된 사용자에게만 보여줄 내부 공지사항에 적합.

### 왜 법적 경고문이 중요한가?

단순한 형식이 아니라 **법적 효력**이 있다. 미국 등 여러 국가에서 네트워크 장비에 "권한 없는 접근 금지" 경고문이 없으면, 무단 접속자를 법적으로 처벌하기 어려울 수 있다. 보안 감사에서도 배너 유무를 점검 항목으로 포함하는 경우가 많다.

### 주의사항

- `welcome`, `환영합니다` 같은 문구는 피해야 한다. 법적으로 접속을 환영한 것으로 해석될 여지가 있다.
- `^C`는 구분자(delimiter)로, 배너 내용에 포함되지 않는 아무 문자를 사용할 수 있다.
- 배너 내용에 호스트명, IP, IOS 버전 등 장비 정보를 포함하지 않는 것이 보안상 좋다.

## 17. SNMP 보안 (v2c vs v3)

SNMP는 네트워크 모니터링에 필수적이지만, 잘못 설정하면 장비 전체 설정이 외부로 노출되거나 변경될 수 있는 위험한 서비스다.

### SNMPv2c의 문제점

```
snmp-server community public RO
snmp-server community private RW
```

v2c는 community string이 **평문으로 전송**된다. 위와 같이 기본값 `public`/`private`를 쓰면 네트워크에서 패킷 캡처만으로 community string을 알아낼 수 있고, `private`가 RW이면 SNMP로 **설정 변경까지 가능**하다. 실제로 SNMP를 통해 라우팅 테이블을 조작하거나 컨피그를 TFTP로 빼내는 공격이 존재한다.

### v2c를 써야 한다면 최소한의 보안

장비나 NMS가 v3를 지원하지 않는 경우, 다음과 같이 ACL을 반드시 적용한다.

```
ip access-list standard SNMP_ACL
 permit host 192.168.250.249     ← NMS 서버
 permit 10.50.100.0 0.0.1.255   ← 모니터링 대역
 deny any log

snmp-server community Xk9$mNpQ2 RO SNMP_ACL    ← 유추 불가능한 문자열 + ACL
snmp-server community Yz7!rTvW8 RW SNMP_ACL    ← RW는 정말 필요할 때만
```

핵심 원칙:

- community string에 `public`, `private`, 회사명 등 유추 가능한 문자열 사용 금지
- **RW community는 정말 필요한 경우에만** 설정 (대부분 RO로 충분)
- 반드시 ACL로 접근 IP 제한

### SNMPv3 구성 (권장)

```
ip access-list standard snmp_server
 permit 10.50.246.201
 permit 10.50.100.0 0.0.1.255
 deny any log

snmp-server group MONITORING v3 priv read READONLY-VIEW access snmp_server
snmp-server view READONLY-VIEW iso included
snmp-server view READONLY-VIEW snmpUsmMIB excluded        ← 인증 정보 제외
snmp-server view READONLY-VIEW snmpVacmMIB excluded       ← 접근 제어 정보 제외
snmp-server view READONLY-VIEW snmpCommunityMIB excluded  ← community 정보 제외
snmp-server user monitor MONITORING v3 auth sha AuthPass123 priv aes 128 PrivPass456
```

v3의 보안 레벨:

|레벨|키워드|인증|암호화|설명|
|---|---|---|---|---|
|noAuthNoPriv|`noauth`|❌|❌|v2c와 동일 수준 (의미 없음)|
|authNoPriv|`auth`|✅|❌|인증만 (패킷 내용은 평문)|
|authPriv|`priv`|✅|✅|인증 + 암호화 (권장)|

### View로 민감 정보 제외

`snmpVacmMIB`, `snmpUsmMIB`, `snmpCommunityMIB`를 View에서 제외하면 SNMP를 통해 다른 SNMP 계정 정보나 community string을 조회할 수 없다. 모니터링 목적으로는 이 MIB들이 불필요하므로 항상 제외하는 것이 좋다.

## 18. 포트 보안 (Port-Security, Storm-Control, BPDU Guard)

접근 제어는 관리 접속(VTY, 콘솔)뿐 아니라 **물리적 포트 레벨**에서도 이루어져야 한다.

### Port-Security

허용되지 않은 MAC 주소를 가진 장비가 포트에 연결되면 차단하는 기능이다.

```
interface GigabitEthernet1/0/1
 switchport mode access
 switchport port-security                       ← 기능 활성화
 switchport port-security violation restrict     ← 위반 시 동작
 switchport port-security aging time 1           ← MAC 에이징 시간(분)
 switchport port-security aging type inactivity  ← 비활성 시 에이징
```

위반 시 동작 모드:

|모드|동작|포트 상태|로그|SNMP trap|
|---|---|---|---|---|
|shutdown|포트 err-disable|비활성화|✅|✅|
|restrict|위반 프레임 드롭|유지|✅|✅|
|protect|위반 프레임 드롭|유지|❌|❌|

**shutdown**이 가장 강력하지만, CCTV나 IoT 장비가 많은 환경에서는 오탐으로 포트가 내려가는 문제가 있어서 **restrict**를 많이 사용한다. restrict는 위반 프레임만 버리고 포트는 유지하면서 로그를 남긴다.

**err-disable 자동 복구 설정**:

```
errdisable recovery cause psecure-violation
errdisable recovery interval 300    ← 5분 후 자동 복구
```

shutdown 모드를 사용할 경우, 수동으로 `shutdown` → `no shutdown`을 치러 가지 않아도 되도록 자동 복구를 설정해두는 것이 운영 편의성에 좋다.

### Storm-Control

브로드캐스트/멀티캐스트 폭풍(storm)을 방지한다. DDoS나 루프 발생 시 네트워크 전체가 마비되는 것을 막아준다.

```
interface GigabitEthernet1/0/1
 storm-control broadcast level 60.00 40.00    ← 60% 도달 시 차단, 40% 이하로 내려가면 해제
 storm-control action shutdown                ← 임계치 초과 시 포트 셧다운
```

- 첫 번째 값(60.00): upper threshold — 이 비율을 넘으면 차단 시작
- 두 번째 값(40.00): lower threshold — 이 비율 아래로 내려가면 차단 해제
- `action shutdown`이면 포트가 err-disable 상태가 되므로 `errdisable recovery cause storm-control`과 함께 설정하는 것이 좋다

### BPDU Guard

STP가 동작하면 안 되는 엔드 디바이스 포트(PC, 서버, CCTV 등)에서 BPDU를 수신하면 포트를 차단한다. 누군가 허가 없이 스위치를 연결해서 STP 토폴로지를 교란하는 것을 방지한다.

```
! 글로벌 설정 (portfast가 설정된 모든 포트에 일괄 적용)
spanning-tree portfast bpduguard default

! 인터페이스별 개별 설정
interface GigabitEthernet1/0/1
 spanning-tree portfast
 spanning-tree bpduguard enable
```

글로벌로 `spanning-tree portfast bpduguard default`를 설정하면, `portfast`가 켜진 모든 포트에 자동으로 BPDU Guard가 적용된다. 엔터프라이즈 환경에서 이 설정이 자주 사용된다.

### 세 가지를 조합한 엔터프라이즈 액세스 포트 템플릿

```
interface GigabitEthernet1/0/1
 description ## CCTV_Camera ##
 switchport access vlan 170
 switchport mode access
 switchport port-security violation restrict
 switchport port-security aging time 1
 switchport port-security aging type inactivity
 switchport port-security
 load-interval 30
 storm-control broadcast level 60.00 40.00
 storm-control action shutdown
 spanning-tree portfast
 ! (글로벌 bpduguard default가 있으면 별도 설정 불필요)
```

## 19. Logging 설정

장비에서 발생하는 이벤트를 기록하고 외부로 전송하는 설정이다. 접근 제어와 직접 연관되는 것은 아니지만, **누가 접속했는지, 어떤 변경이 있었는지 추적**하려면 로깅이 필수다.

### 로깅 대상 종류

|대상|명령어|특징|
|---|---|---|
|Console|`logging console [level]`|콘솔 세션에 실시간 출력. 과도하면 CPU 부하|
|Buffer|`logging buffered [size] [level]`|장비 RAM에 저장. 재부팅 시 삭제|
|Syslog 서버|`logging host [IP]`|외부 서버로 전송. 영구 보관 가능|
|Terminal|`terminal monitor`|VTY 세션에서 로그 확인 (기본 비활성)|

### Severity Level

|레벨|이름|설명|
|---|---|---|
|0|emergencies|시스템 사용 불가|
|1|alerts|즉시 조치 필요|
|2|critical|심각한 상태|
|3|errors|에러 발생|
|4|warnings|경고|
|5|notifications|정상이지만 중요한 이벤트|
|6|informational|정보성 메시지|
|7|debugging|디버그 메시지|

레벨을 지정하면 **해당 레벨 이하(더 심각한 것)**의 메시지만 출력된다. 예를 들어 `logging console critical`이면 레벨 0~2만 콘솔에 표시된다.

### 실무 로깅 구성 예시

```
! 콘솔: 심각한 메시지만 (CPU 부하 방지)
logging console critical

! 버퍼: 정보성까지 충분히 저장
logging buffered 1000000 informational

! Syslog 서버로 전송 (이중화)
logging host 10.50.101.121
logging host 10.150.101.121
logging trap informational             ← Syslog로 보낼 최소 레벨

! 타임스탬프에 로컬 시간대 포함
service timestamps log datetime msec localtime show-timezone

! 시퀀스 번호 추가 (동일 시각 메시지 구분)
service sequence-numbers

! source-interface 지정 (관리 인터페이스에서 발송)
logging source-interface Vlan70
```

### logging discriminator (고급)

특정 패턴의 로그를 필터링할 수 있다. 실무에서 자주 볼 수 있는 설정 예시:

```
logging discriminator Nolog facility drops SMART_LIC
logging buffered discriminator Nolog 1000000
```

이 설정은 Smart License 관련 로그(인터넷 미연결 환경에서 반복 발생)를 버퍼에 기록하지 않도록 필터링한다. 불필요한 로그가 버퍼를 채우는 것을 방지한다.

### 접근 제어와 로깅의 관계

|접근 제어 이벤트|로그 확인 방법|
|---|---|
|SSH 로그인 성공/실패|`show logging \| include SSH`|
|ACL deny 로그|`show logging \| include denied`|
|port-security 위반|`show logging \| include PSECURE`|
|설정 변경|`show logging \| include CONFIG`|
|AAA 인증 실패|Syslog 서버 또는 TACACS+ accounting 로그|

## 20. Management Plane 보호

장비의 관리 트래픽(SSH, SNMP, NTP, TACACS+ 등)을 데이터 트래픽과 분리하여 보호하는 개념이다.

### Management Plane이란?

네트워크 장비의 트래픽은 세 가지 plane으로 분류된다.

|Plane|역할|예시|
|---|---|---|
|Data Plane|사용자 트래픽 전달|PC 간 통신, 웹 트래픽|
|Control Plane|라우팅/스위칭 프로토콜|OSPF, BGP, STP, ARP|
|Management Plane|장비 관리|SSH, SNMP, NTP, Syslog, TACACS+|

접근 제어 설정(SSH, TACACS+, SNMP 등)은 모두 Management Plane에 속한다. 이 plane을 보호하지 않으면 아무리 강력한 인증을 설정해도 DDoS로 관리 접속 자체가 불가능해질 수 있다.

### MPP (Management Plane Protection)

특정 인터페이스만 관리 트래픽을 수신하도록 제한한다.

```
control-plane host
 management-interface Vlan70 allow ssh snmp
```

이 설정을 하면 Vlan70을 통해서만 SSH와 SNMP 접속이 가능하고, 다른 인터페이스로 들어오는 관리 트래픽은 차단된다.

### CoPP (Control Plane Policing)

Control Plane으로 향하는 트래픽에 QoS 정책을 적용하여 과도한 트래픽을 제한한다.

```
! 관리 트래픽 분류
ip access-list extended MGMT-TRAFFIC
 permit tcp any any eq 22         ← SSH
 permit udp any any eq 161        ← SNMP
 permit tcp any any eq 49         ← TACACS+

class-map match-all MGMT-CLASS
 match access-group name MGMT-TRAFFIC

! 정책 적용
policy-map COPP-POLICY
 class MGMT-CLASS
  police rate 500 pps             ← 초당 500패킷으로 제한
   conform-action transmit
   exceed-action drop

control-plane
 service-policy input COPP-POLICY
```

CoPP는 CCNP ENCOR 시험 범위이며 실무에서도 대규모 네트워크에서 사용된다. SSH 브루트포스 공격이 들어와도 CPU가 과부하에 빠지지 않도록 보호하는 역할을 한다.

### Management VRF (OOB 관리)

관리 트래픽을 별도의 VRF로 완전히 분리하는 방식이다. 데이터 트래픽과 관리 트래픽이 물리적 또는 논리적으로 분리되어 보안성이 높다.

```
! Management VRF 생성
vrf definition MGMT
 address-family ipv4

! 관리 인터페이스에 VRF 적용
interface Vlan70
 vrf forwarding MGMT
 ip address 10.140.77.25 255.255.255.0

! TACACS+ source를 VRF에 바인딩
aaa group server tacacs+ CORP
 ip vrf forwarding MGMT
 ip tacacs source-interface Vlan70
```

**OOB (Out-of-Band) 관리 네트워크**는 데이터 네트워크와 물리적으로 분리된 별도의 관리 네트워크를 의미한다. 데이터 네트워크에 장애가 발생해도 관리 접속이 가능하다는 것이 핵심 장점이다.

|관리 방식|설명|장점|단점|
|---|---|---|---|
|In-Band|데이터 네트워크를 통해 관리|별도 인프라 불필요|장애 시 관리 불가|
|OOB|별도 관리 네트워크|장애 독립적|추가 인프라 비용|
|VRF 분리|같은 물리 장비에서 논리 분리|중간 수준 분리|완전한 물리 분리는 아님|


### 액세스 포트 보안 템플릿

새 액세스 포트를 활성화할 때 적용하는 템플릿이다.

```
interface GigabitEthernet1/0/[N]
 description ## [DESCRIPTION] ##
 switchport access vlan [VLAN_ID]
 switchport mode access
 switchport port-security violation restrict
 switchport port-security aging time 1
 switchport port-security aging type inactivity
 switchport port-security
 load-interval 30
 storm-control broadcast level 60.00 40.00
 storm-control action shutdown
 spanning-tree portfast
```

### 사용하지 않는 포트 비활성화 템플릿

```
interface range GigabitEthernet1/0/[START] - [END]
 description ## UNUSED ##
 switchport access vlan 999
 switchport mode access
 shutdown
 spanning-tree portfast
```

사용하지 않는 포트는 반드시 shutdown하고 사용하지 않는 VLAN(예: 999)에 할당하여 실수로 트래픽이 흐르지 않도록 한다.

## 부록 C. CCNP ENCOR 시험 관련 포인트

이 문서에서 다룬 내용 중 CCNP ENCOR (350-401) 시험에서 출제될 수 있는 핵심 포인트를 정리한다.

### Infrastructure Security (시험 비중 약 20%)

**AAA 관련 출제 포인트**

- `aaa new-model` 입력 시 즉시 모든 line에 로컬 인증이 적용되는 동작
- TACACS+ vs RADIUS 차이: TACACS+는 TCP 49, 전체 암호화, 명령어별 권한 제어 가능. RADIUS는 UDP 1812/1813, 패스워드만 암호화, 주로 네트워크 접근 제어용
- 메서드 리스트에서 **ERROR(서버 무응답)일 때만 폴백**, FAIL(인증 거부)에서는 폴백하지 않는 동작
- default 메서드 리스트 vs named 메서드 리스트의 적용 범위 차이
- Authorization: `if-authenticated` 키워드의 의미 — TACACS+ 서버가 응답 없을 때 로컬 인증 통과한 사용자에게 권한 부여

**Control Plane / Management Plane 보호**

- CoPP (Control Plane Policing) 개념과 적용 방법
- Management Plane Protection (MPP) 개념
- 3가지 Plane (Data/Control/Management)의 구분과 각각의 보안 위협

**인프라 보안 설정**

- Port-security violation 모드 3가지 (shutdown/restrict/protect)의 차이
- BPDU Guard vs BPDU Filter 차이: Guard는 BPDU 수신 시 포트 차단, Filter는 BPDU 송수신 자체를 차단
- Storm-control 동작 원리
- ACL을 이용한 VTY 접근 제한
- SNMPv2c vs SNMPv3 보안 차이

### 시험에서 자주 나오는 함정

|함정|정답|
|---|---|
|`login`과 `login local`의 차이?|`login`은 line 패스워드, `login local`은 로컬 DB|
|TACACS+가 FAIL을 반환하면?|local로 폴백 안 함. ERROR(무응답)만 폴백|
|`enable password`와 `enable secret` 동시 설정 시?|`enable secret`이 우선|
|`aaa new-model` 입력 후 바로 텔넷 세션이 끊기는 이유?|기본 인증이 로컬로 변경되나 계정이 없어서|
|port-security에서 protect와 restrict의 차이?|둘 다 프레임 드롭, restrict만 로그/SNMP trap 발생|
|standard ACL을 VTY에 적용할 때 in/out 의미?|in = 장비로 들어오는 접속, out = 장비에서 나가는 접속|
|CoPP는 어느 plane을 보호?|Control Plane (Management 포함)|
|SNMPv3 authPriv에서 priv가 의미하는 것?|패킷 암호화 (privacy)|

### 학습 우선순위

이 문서의 내용을 CCNP ENCOR 시험 관점에서 우선순위를 매기면:

1. **필수**: AAA 동작 원리 (메서드 리스트, 폴백, TACACS+ vs RADIUS)
2. **필수**: Port-security, BPDU Guard, Storm-control 동작 및 차이
3. **필수**: CoPP, MPP 개념
4. **중요**: SNMPv3 보안 레벨, ACL 기반 VTY 접근 제한
5. **참고**: 패스워드 Type 차이, Privilege Level, line 종류
