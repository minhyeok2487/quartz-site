# 1. 왜 통합 모니터링인가?

지금까지 우리는 다섯 가지 핵심 기술을 배웠습니다.

| 장 | 기술 | 역할 |
|----|------|------|
| [[01_SNMP 기초(Simple Network Management Protocol)|01장]] | SNMP | 장비 상태 수집 |
| [[02_Syslog와 로그 관리|02장]] | Syslog | 이벤트 기록 |
| [[03_Zabbix를 활용한 네트워크 모니터링|03장]] | Zabbix | 중앙 관리/시각화 |
| [[04_IP SLA(Cisco IP SLA)|04장]] | IP SLA | 품질 측정 |
| [[05_SLA(서비스 수준 관리)와 네트워크 품질 지표|05장]] | SLA | 품질 지표/계약 |

이것들을 개별적으로 운영하면 어떻게 될까요?

"SNMP Trap은 왔는데 Syslog에는 안 남아있어요", "Zabbix에서는 알림이 왔는데 어떤 장비인지 모르겠어요", "IP SLA 데이터는 장비에만 있고 중앙에서는 못 봐요"... 이런 상황이 벌어집니다. 마치 CCTV, 출입 기록, 순찰 보고서를 각각 다른 곳에서 관리하면 범인을 잡기 어려운 것과 같아요.

**통합 모니터링** 은 이 모든 도구를 하나의 체계로 엮어서 **데이터를 한곳에 모으고, 하나의 대시보드에서 보고, 하나의 프로세스로 대응** 하는 것입니다.

# 2. 통합 모니터링 아키텍처

전체 그림을 먼저 보겠습니다. 이 구성도를 이해하면 통합 모니터링의 80%는 파악한 것입니다.

```
┌──────────────────────────────────────────────────────────────────┐
│                    통합 모니터링 아키텍처                           │
├──────────────────────────────────────────────────────────────────┤
│                                                                  │
│  ┌─────────────────── 관리 VLAN (VLAN 99) ──────────────────┐   │
│  │                                                           │   │
│  │   ┌──────────┐  ┌──────────┐  ┌──────────┐               │   │
│  │   │ Zabbix   │  │ Syslog   │  │ NTP      │               │   │
│  │   │ Server   │  │ Server   │  │ Server   │               │   │
│  │   │ .99.50   │  │ .99.10   │  │ .99.20   │               │   │
│  │   └────┬─────┘  └────┬─────┘  └────┬─────┘               │   │
│  │        │              │              │                     │   │
│  │   ─────┴──────────────┴──────────────┴──── L2 Mgmt SW ── │   │
│  │                                                           │   │
│  └───────────────────────┬───────────────────────────────────┘   │
│                          │ (관리 트래픽만)                         │
│  ────────────────────────┼──────────────────────────────────     │
│                          │                                       │
│   ┌──────────────────────┼──────────────────────────────┐       │
│   │          운영 네트워크 (사용자 VLAN)                    │       │
│   │                      │                               │       │
│   │    ┌──────┐    ┌──────┐    ┌──────┐                 │       │
│   │    │코어SW│────│분배SW│────│액세스SW│                │       │
│   │    └──┬───┘    └──┬───┘    └──┬───┘                 │       │
│   │       │           │           │                      │       │
│   │    ┌──┴───┐    ┌──┴───┐    ┌──┴───┐                │       │
│   │    │라우터 │    │  WLC │    │ 서버  │                │       │
│   │    └──────┘    └──────┘    └──────┘                 │       │
│   │                                                      │       │
│   │  각 장비에서:                                         │       │
│   │  - SNMP → Zabbix (UDP 161/162)                       │       │
│   │  - Syslog → Syslog Server (UDP 514)                  │       │
│   │  - IP SLA → Zabbix (RTTMON MIB 폴링)                 │       │
│   │  - NTP ← NTP Server (시간 동기화)                     │       │
│   │                                                      │       │
│   └──────────────────────────────────────────────────────┘       │
│                                                                  │
└──────────────────────────────────────────────────────────────────┘
```

## 핵심 설계 원칙

### 원칙 1: 관리 VLAN 분리

모니터링 트래픽(SNMP, Syslog)은 **사용자 트래픽과 분리** 해야 합니다. 이유는 두 가지예요.

1. **보안**: SNMP Community String이 사용자 네트워크에 노출되면 안 됩니다
2. **안정성**: 사용자 트래픽이 폭주해도 모니터링은 계속 동작해야 합니다

모든 장비에 관리 VLAN용 인터페이스(SVI 또는 Loopback)를 할당하고, 이 IP로만 SNMP/Syslog를 주고받도록 설정하세요.

### 원칙 2: NTP 시간 동기화

**모든 장비의 시간이 일치** 해야 합니다. 장애 분석 시 "스위치 로그에는 10:03이고, 라우터 로그에는 10:07이면" 인과관계를 파악할 수 없어요.

```bash
! 모든 네트워크 장비에 설정
Router(config)# ntp server 192.168.99.20
Router(config)# clock timezone KST 9
Router(config)# service timestamps log datetime msec localtime show-timezone
```

### 원칙 3: 소스 인터페이스 통일

SNMP, Syslog, NTP의 소스 인터페이스를 **Loopback** 으로 통일합니다. 그래야 어떤 경로로 패킷이 나가든 같은 소스 IP를 사용하죠.

```bash
Router(config)# snmp-server source-interface Loopback0
Router(config)# logging source-interface Loopback0
Router(config)# ntp source Loopback0
```

# 3. 규모별 구성 가이드

네트워크 규모에 따라 모니터링 구성도 달라져야 합니다. 소규모 환경에 대규모 설계를 적용하면 과잉이고, 대규모 환경에 소규모 설계를 적용하면 감당이 안 됩니다.

## 소규모: 장비 50대 미만

**대상:** 중소기업, 소규모 지사, 학원/학교

```
┌──────────┐
│ Zabbix   │ ← All-in-One (Server + DB + Frontend + Syslog)
│ (1대)    │
└────┬─────┘
     │
  ┌──┴──────────────────┐
  │ 스위치/라우터/AP/서버 │
  │   (50대 미만)        │
  └─────────────────────┘
```

**구성:**
- Zabbix Server 1대 (모든 기능 통합)
- rsyslog를 같은 서버에서 실행
- 별도 Proxy 불필요

**하드웨어 사양:**
- CPU: 2~4코어
- RAM: 4~8GB
- 디스크: 100GB SSD

**이 정도면 충분합니다.** 장비 50대 미만이면 Zabbix 한 대가 거뜬히 처리해요. 서버를 한 대만 관리하면 되니 운영 부담도 적습니다.

## 중규모: 장비 50~500대

**대상:** 중견기업, 여러 지사 보유 기업, IDC

```
┌──────────────────────────────┐
│         본사 (서울)            │
│                              │
│  ┌────────┐  ┌────────┐     │
│  │ Zabbix │  │ Syslog │     │
│  │ Server │  │ Server │     │
│  │ + DB   │  │(rsyslog)│    │
│  └───┬────┘  └───┬────┘     │
│      │           │           │
│   ───┴───────────┴───        │
│      │                       │
└──────┼───────────────────────┘
       │ WAN
┌──────┼───────────────────────┐
│      │    부산 지사            │
│  ┌───┴────┐                  │
│  │ Zabbix │                  │
│  │ Proxy  │                  │
│  └───┬────┘                  │
│      │                       │
│   장비들                      │
└──────────────────────────────┘
```

**구성:**
- Zabbix Server 1대 (본사)
- Syslog Server 별도 1대
- 원격 사이트에 Zabbix Proxy 배치
- DB 튜닝 필요 (파티셔닝 적용)

**하드웨어 사양 (Zabbix Server):**
- CPU: 4~8코어
- RAM: 16~32GB
- 디스크: 500GB ~ 1TB SSD

## 대규모: 장비 500대 이상

**대상:** 대기업, ISP, 통신사, 대형 IDC

```
┌──────────────────────────────────────────────────────┐
│                    서울 본사                           │
│                                                      │
│  ┌────────┐  ┌────────┐  ┌────────┐  ┌────────┐    │
│  │ Zabbix │  │ Zabbix │  │ DB     │  │ Syslog │    │
│  │ Server │  │Frontend│  │(HA)    │  │ Cluster│    │
│  │(Active)│  │(LB)    │  │Primary │  │        │    │
│  │        │  │        │  │+Standby│  │        │    │
│  └────────┘  └────────┘  └────────┘  └────────┘    │
│                                                      │
└──────────────────────────────────────────────────────┘
         │              │              │
    ┌────┴────┐    ┌────┴────┐    ┌────┴────┐
    │ Proxy   │    │ Proxy   │    │ Proxy   │
    │ (부산)   │    │ (대전)   │    │ (해외)   │
    └─────────┘    └─────────┘    └─────────┘
```

**구성:**
- Zabbix Server + 별도 DB 서버 (HA 구성)
- Frontend 서버 분리 (로드 밸런서 적용)
- 다수의 Proxy 배치
- Syslog 클러스터 (ELK Stack 고려)
- 모니터링 시스템 자체의 이중화

**하드웨어 사양 (Zabbix Server):**
- CPU: 16코어 이상
- RAM: 64GB 이상
- 디스크: 고성능 SSD RAID

대규모 환경에서는 **모니터링 시스템 자체를 모니터링** 하는 것도 필요합니다. Zabbix가 죽었는데 아무도 모르면 의미가 없잖아요.

# 4. 모니터링 운영 프로세스

도구를 갖춘 것은 절반입니다. 나머지 절반은 **프로세스** 입니다. 장애가 발생했을 때 어떤 순서로 대응하는지, 명확한 프로세스가 있어야 합니다.

## 장애 대응 흐름

```
┌─────────┐    ┌─────────┐    ┌─────────┐    ┌─────────┐    ┌─────────┐
│  감지    │───►│  알림    │───►│  확인    │───►│  대응    │───►│  기록    │
│         │    │         │    │         │    │         │    │         │
│ Zabbix  │    │ 이메일   │    │ 담당자가 │    │ 원인분석 │    │ 장애     │
│ Trigger │    │ Telegram│    │ 대시보드 │    │ 조치수행 │    │ 보고서   │
│ 발생    │    │ SMS     │    │ 확인     │    │ 복구확인 │    │ 작성     │
└─────────┘    └─────────┘    └─────────┘    └─────────┘    └─────────┘
    1분 이내       즉시          5분 이내      상황에 따라       복구 후 24시간
```

### 1단계: 감지

- Zabbix Trigger가 이상 상태를 감지
- SNMP Trap 또는 Syslog 이벤트 수신
- IP SLA Tracking Object 상태 변경

### 2단계: 알림

- Zabbix Action에 의해 자동 알림 발송
- **Escalation** 적용: 5분 미응답 → 팀장, 15분 미응답 → 부서장
- 알림 채널: 이메일(상세 정보) + Telegram/카카오톡(즉시 확인)

### 3단계: 확인

- 담당자가 Zabbix 대시보드에서 장애 범위 파악
- 영향받는 장비, 서비스, 사용자 범위 확인
- [[01_원격 접속(Telnet & SSH)|원격 접속(SSH)]]으로 장비 접속

### 4단계: 대응

- 원인 분석: [[02_Syslog와 로그 관리|Syslog]] 로그 확인, SNMP 데이터 분석
- 조치 수행: 설정 변경, 장비 재시작, 회선 전환 등
- 복구 확인: Zabbix에서 Trigger가 해제(RESOLVED)되었는지 확인

### 5단계: 기록

- 장애 보고서 작성 (발생 시각, 원인, 조치, 복구 시각, 재발 방지)
- [[05_SLA(서비스 수준 관리)와 네트워크 품질 지표|SLA]] 위반 여부 판단
- 필요 시 프로세스/설정 개선

## Alert Fatigue (알림 피로) 방지

알림이 너무 많으면 오히려 문제입니다. 하루에 알림이 100개 오면, 정작 중요한 알림을 놓치게 돼요. 이것을 **Alert Fatigue** 라고 합니다.

**방지 방법:**

| 방법 | 설명 |
|------|------|
| **Trigger 임계값 조정** | 너무 민감하게 설정하지 않기 (CPU 50% → 경고? 너무 낮음) |
| **Severity별 알림 분리** | Disaster만 전화/SMS, Warning은 이메일만 |
| **유지보수 시간 설정** | 예정된 작업 시간에는 알림 억제 |
| **의존성 설정** | 코어 스위치가 Down이면 액세스 스위치 알림은 억제 |
| **반복 알림 제한** | 같은 Trigger에 대해 반복 알림 간격 설정 |

**의존성(Dependency) 설정** 이 특히 중요합니다. 코어 스위치가 죽으면 하위 장비 50대가 전부 알림을 보냅니다. 하지만 실제 문제는 코어 스위치 한 대잖아요. Zabbix에서 Trigger 의존성을 설정하면 "코어 스위치 Down일 때 하위 장비 알림은 억제"할 수 있습니다.

# 5. 실무 체크리스트

## 신규 장비 등록 시 체크리스트

새 장비를 네트워크에 추가했을 때, 모니터링 설정에서 빼먹기 쉬운 항목들을 정리했습니다.

| 순서 | 항목 | 명령어/설정 |
|------|------|-----------|
| 1 | 관리 IP 할당 (관리 VLAN) | `interface vlan 99` + `ip address` |
| 2 | NTP 설정 | `ntp server 192.168.99.20` |
| 3 | Timestamp 설정 | `service timestamps log datetime msec localtime show-timezone` |
| 4 | SNMP Community 설정 | `snmp-server community ... RO 99` |
| 5 | SNMP Trap 설정 | `snmp-server host ...` + `enable traps` |
| 6 | Syslog 설정 | `logging host ...` + `logging trap informational` |
| 7 | Logging source-interface | `logging source-interface Loopback0` |
| 8 | SNMP source-interface | `snmp-server source-interface Loopback0` |
| 9 | Zabbix에 Host 등록 | Template 적용, SNMP Interface 설정 |
| 10 | Zabbix 데이터 수집 확인 | Latest Data에서 데이터 유입 확인 |
| 11 | 네트워크 맵에 추가 | Zabbix 맵에 장비와 링크 추가 |
| 12 | IP SLA 설정 (필요 시) | WAN 구간, ISP 게이트웨이 모니터링 |

## 정기 점검 체크리스트

월 1회 또는 분기 1회 수행하면 좋은 점검 항목입니다.

| 항목 | 확인 사항 | 빈도 |
|------|-----------|------|
| Zabbix 서버 상태 | CPU/메모리/디스크, DB 크기 | 월 1회 |
| 미등록 장비 확인 | 네트워크에 있지만 Zabbix에 없는 장비 | 월 1회 |
| Trigger 검토 | 불필요한 알림, 임계값 적절성 | 분기 1회 |
| Template 업데이트 | 새 버전 Template 적용 여부 | 분기 1회 |
| Housekeeping 확인 | 데이터 보관 기간, DB 파티셔닝 상태 | 월 1회 |
| SLA 보고서 생성 | 가용성, 성능 지표, SLA 충족 여부 | 월 1회 |
| Community String 변경 | 보안을 위한 정기 변경 | 분기 1회 |
| 비상 연락망 확인 | 알림 수신 대상, 연락처 최신화 | 분기 1회 |

## SLA 보고 프로세스

```
매일     → Zabbix 대시보드 확인 (이상 징후 사전 감지)
매주     → 주간 장애 현황 요약 (팀 내부 공유)
매월     → 월간 SLA 보고서 작성 (가용성, 성능, 장애 분석)
분기     → 분기 리뷰 (추세 분석, 개선 계획, 용량 계획)
반기/연간 → ISP SLA 검증, 계약 갱신 검토
```

# 6. 다른 문서와의 연결

통합 모니터링은 단독으로 존재하지 않습니다. 네트워크의 다른 영역과 밀접하게 연결되어 있어요. 기존 문서들과의 연결 포인트를 정리합니다.

## 방화벽 모니터링

[[01_방화벽과 체크포인트|방화벽]]도 SNMP/Syslog를 지원합니다. 방화벽의 CPU 사용률, 세션 수, 트래픽 로그를 Zabbix에서 모니터링할 수 있어요.

**모니터링 항목:**
- 방화벽 CPU/메모리 사용률
- 동시 세션 수 (세션 테이블 Full 감지)
- 차단된 트래픽 로그 (Syslog)
- VPN 터널 상태

## Cisco ISE 모니터링

[[01_Cisco ISE 개요와 아키텍처|Cisco ISE]]에서 SNMP를 활성화하면 ISE 서버 자체의 상태를 모니터링할 수 있습니다. 또한 ISE의 [[07_프로파일링|프로파일링 기능]]은 SNMP Probe를 사용해서 네트워크 장비에서 정보를 수집하는데, 이는 모니터링 영역과 겹치는 부분이에요.

**모니터링 항목:**
- ISE 서버 가용성
- 인증 성공/실패 통계
- RADIUS 응답 시간

## 원격 접속과의 연관

[[01_원격 접속(Telnet & SSH)|원격 접속(SSH)]] 설정에서 Syslog로 로그인 기록을 남기도록 설정하면, "누가 언제 장비에 접속했는지"를 중앙에서 추적할 수 있습니다. 장애 발생 전 누가 설정을 변경했는지 확인하는 데 핵심적인 정보입니다.

## 포트 보안 이벤트

[[08_Port Security(포트 보안)|포트 보안]] 위반이 발생하면 SNMP Trap과 Syslog가 동시에 생성됩니다. Zabbix에서 이를 감지하면 "어떤 포트에서, 어떤 MAC 주소가, 언제 위반했는지" 자동으로 알림을 받을 수 있어요.

## EtherChannel, OSPF 모니터링

[[09_EtherChannel|EtherChannel]]이나 [[03_OSPF 라우팅 프로토콜|OSPF]] 상태 변화도 SNMP Trap으로 감지할 수 있습니다. EtherChannel 멤버 포트가 빠지거나 OSPF 네이버가 끊어지면 즉시 알림을 받아야 하죠.

# 7. 정리하며 - 전체 시리즈 요약

6개 장에 걸쳐 네트워크 모니터링의 전 영역을 다뤘습니다. 마지막으로 전체를 되짚어 보겠습니다.

```
┌─────────────────────────────────────────────────────────┐
│           네트워크 모니터링 전체 그림                       │
├─────────────────────────────────────────────────────────┤
│                                                         │
│   [01_SNMP]         장비 상태를 수집하는 프로토콜          │
│       ↓                                                 │
│   [02_Syslog]       이벤트를 기록하는 프로토콜             │
│       ↓                                                 │
│   [03_Zabbix]       수집/기록을 중앙에서 관리하는 NMS      │
│       ↓                                                 │
│   [04_IP SLA]       능동적으로 품질을 측정하는 도구         │
│       ↓                                                 │
│   [05_SLA]          비즈니스 관점의 품질 관리              │
│       ↓                                                 │
│   [06_통합 가이드]   모든 것을 하나로 엮는 실무 체계        │
│                                                         │
└─────────────────────────────────────────────────────────┘
```

**핵심 메시지:**
- **SNMP** 는 장비의 "건강 상태"를 수집합니다 (체온, 혈압, 맥박)
- **Syslog** 는 장비의 "진료 기록"을 남깁니다 (언제 어떤 일이 있었는지)
- **Zabbix** 는 "중앙 관제센터"입니다 (데이터 모으고, 보여주고, 알려줌)
- **IP SLA** 는 "시운전"입니다 (실제 경로의 품질을 직접 측정)
- **SLA** 는 "약속"입니다 (측정한 결과로 서비스 품질을 보증)
- **통합 모니터링** 은 "운영 체계"입니다 (도구 + 프로세스 = 실무)

네트워크 모니터링은 한 번 구축하면 끝이 아닙니다. 장비가 추가될 때마다 등록하고, 임계값은 환경에 맞게 조정하고, 프로세스는 경험을 통해 개선해 나가야 합니다. 처음부터 완벽할 필요는 없어요. 작게 시작해서 점진적으로 확장하면 됩니다.

장비 5대짜리 소규모 환경이라도, SNMP + Syslog + Zabbix를 설정하는 것부터 시작해보세요. 그것만으로도 네트워크 운영의 질이 확연히 달라질 겁니다.

> 문제 | 통합 모니터링 체계에서 "관리 VLAN을 분리해야 하는 이유" 두 가지는?

정답은 → **보안** (SNMP Community String 노출 방지)과 **안정성** (사용자 트래픽 폭주 시에도 모니터링 트래픽 보장)입니다. 관리 트래픽과 사용자 트래픽은 반드시 분리되어야 해요.

---

이것으로 **네트워크 모니터링 시리즈** 를 마칩니다.

처음에는 SNMP라는 단어조차 낯설었을 수도 있지만, 여기까지 읽으신 여러분은 이제 네트워크 모니터링의 전체 그림을 갖고 계십니다. 이론에서 그치지 말고, 실습 환경에서 직접 SNMP를 설정하고, Zabbix를 설치하고, Trigger를 만들어보세요. 손으로 해봐야 진짜 실력이 됩니다.
