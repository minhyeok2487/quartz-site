# 1. SLA란 무엇인가?

"이번 달 가용성 99.9% 달성했습니다." 네트워크 월간 보고서에 이런 문장이 들어갑니다. 그런데 99.9%가 정확히 어느 정도인지 감이 오시나요? 99.9%면 거의 100%니까 엄청 좋은 거 아닌가? 라고 생각할 수 있지만, 계산해보면 놀라실 겁니다.

**99.9% 가용성** = 한 달에 **약 43분** 장애 허용

고작 0.1% 차이인데 43분이나 됩니다! 만약 이 장비가 은행의 인터넷뱅킹 서버라면? 43분 동안 고객이 돈을 못 옮기는 거예요. 이래서 SLA가 중요합니다.

## SLA의 정의

**SLA(Service Level Agreement)** 는 서비스 제공자와 고객 사이에 서비스 품질을 **수치로 약속** 한 계약입니다.

쉽게 말하면 "이 정도 품질은 보장할게요, 못 지키면 페널티 물겠습니다"라는 약속입니다.

```
┌─────────────────────────────────────────────────────────┐
│                     SLA 구조                              │
├─────────────────────────────────────────────────────────┤
│                                                         │
│   ┌──────────┐     SLA 계약     ┌──────────┐            │
│   │ 서비스    │ ◄──────────────► │  고객     │            │
│   │ 제공자    │                  │          │            │
│   │ (ISP 등) │                  │ (우리회사) │           │
│   └──────────┘                  └──────────┘            │
│                                                         │
│   "99.95% 가용성 보장"                                    │
│   "지연 20ms 이내"                                       │
│   "패킷 손실 0.1% 이내"                                   │
│                                                         │
│   ↓ 미달성 시                                            │
│   크레딧 환불, 위약금, 계약 해지 사유                       │
│                                                         │
└─────────────────────────────────────────────────────────┘
```

네트워크 엔지니어 입장에서 SLA는 두 가지 의미가 있습니다:

1. **ISP가 우리에게 약속한 SLA**: ISP 회선의 품질이 약속한 수준인지 확인
2. **우리가 내부 고객에게 약속한 SLA**: 네트워크 인프라의 가용성을 유지

# 2. 네트워크 SLA 핵심 지표

SLA에서 다루는 네트워크 품질 지표는 크게 다섯 가지입니다.

## Availability (가용성) - "9의 법칙"

가용성은 **서비스가 정상 운영된 시간의 비율** 입니다. "파이브 나인(Five Nines)"이라는 표현, 들어보셨을 거예요.

| 가용성 | 연간 허용 장애 시간 | 월간 허용 장애 시간 | 일반적 용도 |
|--------|-------------------|-------------------|-----------|
| **99%** (Two Nines) | 3일 15시간 | 7시간 18분 | 비핵심 시스템 |
| **99.9%** (Three Nines) | 8시간 46분 | 43분 50초 | 일반 기업 |
| **99.95%** | 4시간 23분 | 21분 55초 | ISP 회선 |
| **99.99%** (Four Nines) | 52분 33초 | 4분 23초 | 금융, 의료 |
| **99.999%** (Five Nines) | 5분 15초 | 26초 | 통신사 코어 |

**99%와 99.999%의 차이가 보이시나요?** 9 하나 추가하는 게 얼마나 어려운지, 비용이 얼마나 증가하는지 생각해보세요. 99.999%를 달성하려면 이중화는 기본이고, 장비 자체도 최고급이어야 하고, 운영 프로세스도 완벽해야 합니다.

**가용성 계산 공식:**

```
가용성(%) = (전체 시간 - 장애 시간) / 전체 시간 × 100

예시: 한 달(43,200분) 중 20분 장애 발생
가용성 = (43,200 - 20) / 43,200 × 100 = 99.954%
```

## Latency (지연) - "얼마나 빠른가"

패킷이 출발지에서 목적지까지 가는 데 걸리는 시간입니다. [[04_IP SLA(Cisco IP SLA)|IP SLA]]의 RTT(Round Trip Time)가 바로 이것을 측정합니다.

| 용도 | 양호 | 주의 | 불량 |
|------|------|------|------|
| 웹 브라우징 | < 100ms | 100~300ms | > 300ms |
| VoIP | < 150ms | 150~300ms | > 300ms |
| 실시간 게임 | < 50ms | 50~100ms | > 100ms |
| 화상회의 | < 150ms | 150~400ms | > 400ms |

## Jitter (지터) - "얼마나 일정한가"

패킷 도착 간격의 변동성입니다. VoIP와 화상회의에서 특히 중요해요.

- **Jitter 낮음** = 음성이 깨끗하게 들림
- **Jitter 높음** = 음성이 끊기거나 울림

## Packet Loss (패킷 손실) - "얼마나 안정적인가"

전송된 패킷 중 도착하지 못한 비율입니다.

| 패킷 손실률 | 영향 |
|------------|------|
| **0%** | 완벽 |
| **< 0.1%** | 거의 영향 없음 |
| **0.1% ~ 1%** | TCP는 재전송으로 보완, UDP(VoIP)는 영향 있음 |
| **1% ~ 5%** | 체감되는 품질 저하 |
| **> 5%** | 심각한 서비스 장애 |

## Throughput (처리량) - "얼마나 많이 보내는가"

단위 시간당 실제로 전송할 수 있는 데이터 양입니다. **대역폭(Bandwidth)** 과 혼동하기 쉬운데, 차이가 있어요.

- **대역폭**: 이론적 최대 속도 (도로의 최대 차선)
- **처리량**: 실제로 흐르는 데이터 양 (실제로 지나가는 차량 수)

1Gbps 회선이라도 실제 Throughput은 800Mbps 정도일 수 있습니다. 프로토콜 오버헤드, 패킷 손실, 지연 등이 영향을 미치기 때문이에요.

> 문제 | 99.99% 가용성을 보장하는 서비스의 월간 허용 장애 시간은 약 몇 분인가요?

정답은 → **약 4분 23초** 입니다. 한 달을 43,200분으로 계산하면 0.01% = 4.32분이에요. 이 수준을 달성하려면 장비 이중화가 필수입니다.

# 3. SLA의 종류와 구조

SLA는 누구와 누구 사이의 약속인가에 따라 종류가 나뉩니다.

## ISP SLA (외부 SLA)

ISP(인터넷 서비스 제공자)와 우리 회사 사이의 계약입니다. ISP가 제공하는 회선의 품질을 보장하는 거예요.

**일반적인 ISP SLA 항목:**

| 항목 | 보장 수준 (예시) | 측정 방법 |
|------|----------------|-----------|
| 회선 가용성 | 99.95% | 월간 장애 시간 |
| 지연 (RTT) | < 10ms (국내) | IP SLA / Ping |
| 패킷 손실 | < 0.1% | IP SLA |
| 장애 복구 시간 (MTTR) | < 4시간 | 장애 접수 ~ 복구 완료 |

## 내부 SLA

IT 부서가 사내 다른 부서에 약속하는 서비스 수준입니다.

**예시:**
- "사내 네트워크 가용성 99.9% 보장"
- "VPN 접속 지연 50ms 이내"
- "무선 AP 장애 발생 시 2시간 이내 복구"

## OLA (Operational Level Agreement)

IT 부서 내부의 운영 계약입니다. 예를 들어 네트워크팀과 서버팀 사이의 약속이에요.

**예시:**
- "네트워크팀은 VLAN 변경 요청을 2시간 이내에 처리한다"
- "서버팀은 DNS 장애 발생 시 30분 이내에 대응한다"

## SLA vs OLA vs SLO 비교

| 항목 | SLA | OLA | SLO |
|------|-----|-----|-----|
| **대상** | 고객 ↔ 서비스 제공자 | 내부 팀 ↔ 내부 팀 | 내부 목표 |
| **구속력** | 계약 (위약금 등) | 내부 합의 | 자체 설정 |
| **예시** | ISP 99.95% 보장 | VLAN 변경 2시간 이내 | CPU 80% 미만 유지 |

# 4. SLA 측정 도구와 방법

SLA를 관리하려면 **측정** 이 되어야 합니다. "측정할 수 없으면 관리할 수 없다"는 피터 드러커의 말이 딱 맞는 영역이에요.

## 측정 도구 조합

지금까지 배운 도구들이 SLA 측정에 어떻게 활용되는지 교차 참조해봅시다.

| SLA 지표 | 측정 도구 | 참조 문서 |
|----------|----------|-----------|
| **가용성** | SNMP Polling (ICMP Ping) → Zabbix | [[01_SNMP 기초(Simple Network Management Protocol)|01_SNMP]], [[03_Zabbix를 활용한 네트워크 모니터링|03_Zabbix]] |
| **지연 (Latency)** | IP SLA ICMP Echo → RTTMON MIB → Zabbix | [[04_IP SLA(Cisco IP SLA)|04_IP SLA]] |
| **지터 (Jitter)** | IP SLA UDP Jitter → RTTMON MIB → Zabbix | [[04_IP SLA(Cisco IP SLA)|04_IP SLA]] |
| **패킷 손실** | IP SLA → Zabbix | [[04_IP SLA(Cisco IP SLA)|04_IP SLA]] |
| **처리량** | SNMP ifInOctets/ifOutOctets → Zabbix 그래프 | [[01_SNMP 기초(Simple Network Management Protocol)|01_SNMP]] |
| **장애 시간** | Zabbix Trigger 발생/해제 시간 | [[03_Zabbix를 활용한 네트워크 모니터링|03_Zabbix]] |

이 표를 보면, 앞서 배운 기술들이 어떻게 하나의 SLA 관리 체계로 연결되는지 감이 오시죠?

## 가용성 측정 실습: Zabbix에서 SLA 리포트 생성

Zabbix 7.0부터는 **SLA 기능** 이 내장되어 있습니다.

**설정 경로:** Services → SLA → Create SLA

| 설정 항목 | 값 예시 | 설명 |
|-----------|--------|------|
| Name | 코어 네트워크 SLA | SLA 이름 |
| SLO | 99.95% | 목표 가용성 |
| Effective date | 2026-01-01 | SLA 측정 시작일 |
| Reporting period | Monthly | 월간 보고 |
| Service tags | service: core-network | 대상 서비스 태그 |

이렇게 설정하면 Zabbix가 자동으로 가용성을 계산하고, SLA 보고서를 생성해줍니다. "이번 달 코어 네트워크 가용성 99.97%, SLA 충족" 같은 리포트를 자동으로 받을 수 있어요.

# 5. 실무에서 SLA 관리하기

## ISP 회선 SLA 검증

ISP가 "99.95% 가용성, 지연 10ms 이내"를 약속했다면, 우리가 직접 확인해야 합니다. ISP 말만 믿으면 안 돼요.

**검증 방법:**

1. **IP SLA 설정**: ISP 게이트웨이까지 ICMP Echo 테스트 (5초 간격)
2. **Zabbix 연동**: RTTMON MIB 폴링으로 RTT, 패킷 손실 수집
3. **월간 리포트**: Zabbix SLA 리포트로 가용성/성능 자동 산출

```bash
! ISP 게이트웨이 모니터링용 IP SLA
Router(config)# ip sla 100
Router(config-ip-sla)# icmp-echo 203.0.113.1
Router(config-ip-sla-echo)# frequency 5
Router(config-ip-sla-echo)# timeout 3000
Router(config-ip-sla-echo)# exit
Router(config)# ip sla schedule 100 life forever start-time now
```

## 장애 시 SLA 위반 판단

장애가 발생했을 때 SLA 위반 여부를 판단하는 기준을 미리 정해두어야 합니다.

**판단 기준 예시:**

| 항목 | SLA 기준 | 측정값 | 판단 |
|------|---------|--------|------|
| 월간 가용성 | 99.95% | 99.92% | **SLA 위반** (허용 21분, 실제 34분 장애) |
| RTT | < 10ms | 8ms 평균 | SLA 충족 |
| 패킷 손실 | < 0.1% | 0.05% | SLA 충족 |

SLA 위반 시 ISP에 통보하고, 계약에 따라 크레딧이나 배상을 요청합니다. 이때 **객관적인 데이터(Zabbix 리포트)** 가 있으면 협상에서 유리합니다.

## 보고서 작성

월간 네트워크 보고서에 포함해야 할 SLA 항목:

| 섹션 | 내용 |
|------|------|
| **가용성 현황** | 전체 가용성 %, 장애 건수, 장애 시간 합계 |
| **성능 지표** | 평균/최대 지연, 지터, 패킷 손실률 |
| **주요 장애** | 장애 일시, 원인, 조치 내용, 소요 시간 |
| **추세 분석** | 전월 대비 변화, 3개월/6개월 추이 |
| **SLA 달성 여부** | 각 SLA 항목별 충족/미충족 판정 |
| **개선 계획** | SLA 미달 항목에 대한 개선 방안 |

# 6. SLA와 네트워크 설계

SLA 수준은 네트워크 설계에 직접적인 영향을 미칩니다. 높은 가용성을 약속했다면 그에 맞는 설계가 필요하죠.

## 이중화 설계

```
┌─────────────────────────────────────────────────────────┐
│           가용성 수준에 따른 설계                           │
├─────────────────────────────────────────────────────────┤
│                                                         │
│   99% (단일 구성)          99.99% (이중화 구성)           │
│                                                         │
│     [ISP]                   [ISP-A]    [ISP-B]          │
│       │                       │           │             │
│     [라우터]                [라우터A]  [라우터B]           │
│       │                      \ HSRP  /                  │
│     [스위치]                  [스위치A]──[스위치B]         │
│       │                       │           │             │
│     [서버]                  [서버A]    [서버B]            │
│                                                         │
│   장비 하나 죽으면           어디가 죽어도                 │
│   서비스 중단               서비스 유지                   │
│                                                         │
└─────────────────────────────────────────────────────────┘
```

| 가용성 목표 | 필요한 설계 | 예상 비용 배율 |
|------------|-----------|-------------|
| 99% | 단일 구성 | 1x |
| 99.9% | 핵심 장비 이중화 | 1.5x ~ 2x |
| 99.99% | 전체 경로 이중화 + 자동 전환 | 2x ~ 3x |
| 99.999% | 지리적 이중화 + 무중단 설계 | 5x+ |

## QoS 정책과의 연결

SLA에서 VoIP 품질을 약속했다면, **QoS(Quality of Service)** 정책으로 이를 보장해야 합니다.

- **지연 보장** → 음성 트래픽에 우선순위 큐 적용
- **지터 최소화** → LLQ(Low Latency Queuing) 사용
- **패킷 손실 방지** → 대역폭 확보, WRED 적용

SLA는 약속이고, QoS는 그 약속을 지키기 위한 기술적 수단입니다.

> 문제 | 99.999% 가용성을 달성하기 위해 가장 필수적인 네트워크 설계 원칙은?

정답은 → **이중화(Redundancy)** 입니다. 단일 장애점(SPOF)을 제거하고, 모든 경로에 대해 백업을 구성해야 99.999%에 도달할 수 있습니다. 장비, 회선, 전원, 심지어 데이터센터까지 이중화해야 하는 수준이에요.

# 7. 정리하며

이번 장에서 배운 내용을 정리합니다.

- **SLA** 는 서비스 품질을 수치로 약속한 계약입니다.

- **9의 법칙**: 99.9%는 월 43분, 99.99%는 월 4분 장애 허용. 9 하나 차이가 엄청난 차이입니다.

- 네트워크 SLA 핵심 지표는 **Availability, Latency, Jitter, Packet Loss, Throughput** 5가지입니다.

- SLA 종류: **ISP SLA**(외부), **내부 SLA**(사내), **OLA**(부서 간)

- SLA 측정은 [[01_SNMP 기초(Simple Network Management Protocol)|SNMP]] + [[04_IP SLA(Cisco IP SLA)|IP SLA]] + [[03_Zabbix를 활용한 네트워크 모니터링|Zabbix]]를 조합해서 수행합니다.

- SLA 수준에 따라 **이중화 설계** 와 **QoS 정책** 이 결정됩니다.

- ISP SLA는 우리가 직접 측정하고 검증해야 합니다.
