# 이전 장 요약

이전 장에서는 **OSI 7계층 모델**에 대해 배웠습니다:

**OSI 7계층 구조**:
- **응용 계층 (L7)**: 사용자 인터페이스, HTTP, FTP, SMTP 등
- **표현 계층 (L6)**: 데이터 변환, 암호화, 압축
- **세션 계층 (L5)**: 세션 관리, 동기화
- **전송 계층 (L4)**: 신뢰성 있는 데이터 전송, TCP/UDP
- **네트워크 계층 (L3)**: 라우팅, IP 주소
- **데이터 링크 계층 (L2)**: MAC 주소, 프레임 전송
- **물리 계층 (L1)**: 전기 신호, 케이블

**각 계층의 역할**: 계층화를 통한 문제 해결, 표준화, 독립성 보장

이제 데이터가 각 계층을 거치면서 **실제로 어떻게 처리되는지**, 즉 **캡슐화와 디캡슐화**에 대해 알아봅시다.

---

# 1. 캡슐화와 디캡슐화란?

네트워크를 공부하다 보면 OSI 7 계층이라는 개념을 접하게 됩니다. 각 계층은 서로 독립적으로 동작하면서도 협력하여 데이터를 전송한다고 배웁니다. 그런데 실제로 데이터가 한 컴퓨터에서 다른 컴퓨터로 전송될 때 각 계층에서는 무슨 일이 일어날까요?

여러분이 웹 브라우저로 웹사이트에 접속할 때, 그 데이터는 어떻게 목적지까지 도달하는 걸까요? 단순히 데이터를 그대로 보내는 것이 아닙니다. 각 계층을 지날 때마다 필요한 정보가 추가되고, 목적지에 도착하면 그 정보를 하나씩 벗겨내며 원래의 데이터를 복원합니다.

이 과정에서 **캡슐화(Encapsulation)** 와 **디캡슐화(Decapsulation)** 라는 개념이 핵심적인 역할을 합니다. 캡슐화는 데이터를 보낼 때 각 계층에서 필요한 정보를 추가하는 과정이고, 디캡슐화는 받은 데이터에서 각 계층의 정보를 제거하며 원래 데이터를 얻어내는 과정입니다.

이번 장에서는 캡슐화와 디캡슐화가 무엇인지, 각 계층에서 어떤 일이 일어나는지 상세히 알아보겠습니다.

# 2. 캡슐화(Encapsulation)란?

캡슐화는 상위 계층에서 하위 계층으로 데이터가 내려갈 때마다 각 계층에서 필요한 헤더(Header) 정보를 추가하는 과정입니다. 마치 소포를 포장할 때 상자 안에 물건을 넣고, 그 상자를 다시 큰 상자에 넣고, 거기에 송장을 붙이는 것과 비슷합니다.

## 왜 캡슐화가 필요한가?

각 계층은 서로 다른 역할을 담당합니다:
- **전송 계층(L4)**: 출발지와 목적지 포트 정보, 신뢰성 제어
- **네트워크 계층(L3)**: 출발지와 목적지 IP 주소, 라우팅
- **데이터 링크 계층(L2)**: 출발지와 목적지 MAC 주소, 오류 검출

각 계층이 자신의 역할을 수행하려면 필요한 정보를 데이터에 추가해야 합니다. 이것이 바로 캡슐화의 목적입니다.

> 문제 | 캡슐화는 상위 계층에서 하위 계층으로 갈 때 일어날까요, 하위 계층에서 상위 계층으로 갈 때 일어날까요?

정답은 → 상위 계층에서 하위 계층으로 내려갈 때 일어납니다. 데이터를 보낼 때(송신 측)에 각 계층을 거치며 헤더가 추가됩니다.

# 3. 캡슐화 과정 단계별 이해

캡슐화 과정을 각 계층별로 자세히 살펴보겠습니다. 웹 브라우저로 웹사이트를 방문하는 상황을 예로 들어보겠습니다.

## 1단계: 응용 계층(L7~L5) - 데이터 생성

사용자가 웹 브라우저에서 "www.example.com" 을 입력하면, 응용 계층에서 HTTP 요청 메시지가 생성됩니다. 이것이 우리가 보내려는 실제 **데이터(Data)** 또는 **페이로드(Payload)** 입니다.

```
Data: GET /index.html HTTP/1.1
```

이 단계에서는 순수한 데이터만 존재합니다.

## 2단계: 전송 계층(L4) - 세그먼트/데이터그램 생성

데이터가 전송 계층(Layer 4)으로 내려오면, **TCP 헤더** 또는 **UDP 헤더**가 추가됩니다.

**TCP를 사용하는 경우:**
```
[TCP Header] + [Data] = TCP Segment (세그먼트)
```

TCP 헤더에는 다음과 같은 정보가 포함됩니다:
- **출발지 포트 번호**: 예) 54321 (임의로 할당)
- **목적지 포트 번호**: 예) 80 (HTTP)
- **시퀀스 번호**: 데이터 순서 보장
- **확인 응답 번호**: 신뢰성 제어
- **체크섬**: 오류 검출

**UDP를 사용하는 경우:**
```
[UDP Header] + [Data] = UDP Datagram (데이터그램)
```

UDP 헤더는 TCP보다 간단하며 주로 포트 번호와 길이, 체크섬 정보만 포함합니다.

> 문제 | 웹 브라우저(HTTP)는 일반적으로 TCP를 사용할까요, UDP를 사용할까요?

정답은 → TCP를 사용합니다. HTTP는 신뢰성 있는 데이터 전송이 필요하므로 연결 지향적이고 신뢰성을 보장하는 TCP를 사용합니다. 반면 DNS 조회나 실시간 스트리밍은 UDP를 사용하기도 합니다.

## 3단계: 네트워크 계층(L3) - 패킷 생성

L4 PDU(세그먼트 또는 데이터그램)가 네트워크 계층(Layer 3)으로 내려오면, **IP 헤더**가 추가됩니다.

```
[IP Header] + [TCP Segment] = IP Packet (패킷)
```

IP 헤더에는 다음과 같은 정보가 포함됩니다:
- **출발지 IP 주소**: 예) 192.168.1.100 (내 컴퓨터의 IP)
- **목적지 IP 주소**: 예) 93.184.216.34 (www.example.com의 IP)
- **TTL(Time To Live)**: 패킷 수명
- **프로토콜**: TCP(6) 또는 UDP(17)
- **체크섬**: 헤더 오류 검출

이 단계에서 패킷은 출발지와 목적지 IP 주소를 가지게 되어 인터넷을 통해 라우팅될 수 있습니다.

## 4단계: 데이터 링크 계층(L2) - 프레임 생성

IP 패킷이 데이터 링크 계층(Layer 2)으로 내려오면, **Ethernet 헤더**와 **트레일러(Trailer)** 가 추가됩니다.

```
[Ethernet Header] + [IP Packet] + [Ethernet Trailer] = Ethernet Frame (프레임)
```

Ethernet 헤더에는:
- **출발지 MAC 주소**: 예) AA:BB:CC:DD:EE:01 (내 컴퓨터의 MAC)
- **목적지 MAC 주소**: 예) 11:22:33:44:55:66 (게이트웨이 라우터의 MAC)
- **이더타입(EtherType)**: 상위 프로토콜 식별 (예: 0x0800 = IPv4)

Ethernet 트레일러에는:
- **FCS(Frame Check Sequence)**: CRC-32 알고리즘을 사용한 오류 검출 코드

### ARP의 역할

여기서 중요한 질문이 생깁니다: 목적지 MAC 주소를 어떻게 알 수 있을까요?

IP 주소는 알고 있지만 MAC 주소는 모르는 상황입니다. 이때 **ARP(Address Resolution Protocol)** 가 사용됩니다.

ARP는 IP 주소를 MAC 주소로 변환하는 프로토콜입니다:
1. 컴퓨터가 "192.168.1.1의 MAC 주소가 뭐야?"라고 네트워크에 브로드캐스트
2. 해당 IP를 가진 장비가 "내 MAC 주소는 11:22:33:44:55:66이야"라고 응답
3. 이 정보를 ARP 캐시에 저장하여 다음에 사용

### FCS의 역할

프레임 끝에 추가되는 **FCS(Frame Check Sequence)** 는 전송 중 오류를 검출하기 위한 체크섬입니다. CRC-32(Cyclic Redundancy Check) 알고리즘을 사용하여 계산되며, 수신 측에서 재계산하여 비교함으로써 프레임이 손상되었는지 확인합니다.

## 5단계: 물리 계층(L1) - 신호로 변환

완성된 Ethernet 프레임은 물리 계층(Layer 1)에서 **전기 신호, 광 신호, 또는 무선 신호**로 변환되어 실제 네트워크 매체를 통해 전송됩니다.

- **유선 네트워크**: 전기 신호 (구리선) 또는 광 신호 (광섬유)
- **무선 네트워크**: 무선 주파수 신호 (WiFi, LTE 등)

이렇게 5단계를 거쳐 애플리케이션 데이터가 물리적인 신호로 변환되어 네트워크를 통해 전송됩니다.

# 4. 각 계층의 PDU 이름

캡슐화 과정에서 각 계층마다 데이터의 이름이 달라집니다. 이것을 **PDU(Protocol Data Unit)** 라고 부르며, 각 계층의 데이터 단위를 의미합니다.

| 계층 | PDU 이름 | 포함 내용 |
|------|----------|-----------|
| L7~L5 (응용 계층) | **Data** (데이터) | 애플리케이션 데이터 |
| L4 (전송 계층) | **Segment** (세그먼트) - TCP<br>**Datagram** (데이터그램) - UDP | L4 헤더 + 데이터 |
| L3 (네트워크 계층) | **Packet** (패킷) | L3 헤더 + 세그먼트/데이터그램 |
| L2 (데이터 링크 계층) | **Frame** (프레임) | L2 헤더 + 패킷 + L2 트레일러 |
| L1 (물리 계층) | **Bit** (비트) | 전기·광·무선 신호 |

이 용어들을 정확히 아는 것은 네트워크 전문가와 대화할 때 매우 중요합니다. 예를 들어:
- "패킷이 드롭되고 있어"라고 하면 L3(네트워크 계층) 문제를 의미합니다
- "프레임 에러가 발생하고 있어"라고 하면 L2(데이터 링크 계층) 문제를 의미합니다

> 문제 | TCP 연결에서 데이터를 전송할 때, L4 계층에서의 PDU 이름은?

정답은 → Segment(세그먼트)입니다. UDP를 사용한다면 Datagram(데이터그램)이 됩니다.

# 5. 디캡슐화(Decapsulation)란?

디캡슐화는 캡슐화의 정반대 과정입니다. 수신 측에서 받은 신호를 원래의 데이터로 복원하기 위해 각 계층의 헤더를 제거하는 과정입니다.

포장된 소포를 받아서 송장을 떼고, 큰 상자를 열고, 작은 상자를 열어 최종적으로 내용물을 꺼내는 것과 같습니다.

## 디캡슐화는 언제 일어나는가?

디캡슐화는 데이터를 **수신하는 측**에서 일어납니다. 네트워크를 통해 전송된 신호가 목적지에 도착하면, 하위 계층에서 상위 계층으로 올라가며 각 계층의 헤더를 제거하고 검증합니다.

# 6. 디캡슐화 과정 단계별 이해

이제 수신 측에서 어떻게 데이터를 복원하는지 살펴보겠습니다.

## 1단계: 물리 계층(L1) - 신호 수신

물리 계층에서 **전기 신호, 광 신호, 또는 무선 신호**를 수신합니다. 이 신호를 비트 스트림으로 변환하여 상위 계층(L2)으로 전달합니다.

## 2단계: 데이터 링크 계층(L2) - 프레임 처리

비트 스트림이 데이터 링크 계층으로 올라오면, **Ethernet 프레임**으로 재구성됩니다.

이 단계에서 수행하는 작업:

**1) FCS 검증**
- 수신한 프레임의 FCS를 재계산하여 송신 측에서 계산한 값과 비교합니다
- 값이 다르면 프레임이 손상된 것이므로 폐기합니다
- 값이 같으면 프레임이 정상이므로 계속 처리합니다

**2) MAC 주소 확인**
- 목적지 MAC 주소를 확인합니다
- 자신의 MAC 주소와 일치하거나 브로드캐스트 주소(FF:FF:FF:FF:FF:FF)이면 계속 처리합니다
- 일치하지 않으면 프레임을 폐기합니다 (이 패킷은 자신에게 온 것이 아님)

**3) 헤더와 트레일러 제거**
- Ethernet 헤더와 FCS를 제거하여 **IP 패킷**을 추출합니다
- IP 패킷을 상위 계층(L3)으로 전달합니다

## 3단계: 네트워크 계층(L3) - 패킷 처리

IP 패킷이 네트워크 계층으로 올라오면:

**1) IP 헤더 검증**
- IP 헤더의 체크섬을 검증하여 헤더가 손상되지 않았는지 확인합니다
- TTL(Time To Live) 값을 확인합니다

**2) 목적지 IP 주소 확인**
- 목적지 IP 주소가 자신의 IP 주소인지 확인합니다
- 자신의 IP가 맞으면 계속 처리합니다
- 다른 IP라면 라우팅 테이블을 참조하여 다음 홉(hop)으로 전달합니다 (라우터의 경우)

**3) 프로토콜 식별**
- IP 헤더의 프로토콜 필드를 확인하여 상위 프로토콜이 TCP(6)인지 UDP(17)인지 판단합니다

**4) IP 헤더 제거**
- IP 헤더를 제거하여 **TCP 세그먼트** 또는 **UDP 데이터그램**을 추출합니다
- 이것을 상위 계층(L4)으로 전달합니다

## 4단계: 전송 계층(L4) - 세그먼트/데이터그램 처리

TCP 세그먼트 또는 UDP 데이터그램이 전송 계층으로 올라오면:

**TCP의 경우:**
1. **체크섬 검증**: 세그먼트가 손상되지 않았는지 확인
2. **포트 번호 확인**: 목적지 포트 번호를 보고 어느 애플리케이션으로 전달할지 결정 (예: 80번 포트 → 웹 서버)
3. **시퀀스 번호 확인**: 데이터 순서가 올바른지 확인, 필요하면 재정렬
4. **확인 응답(ACK) 전송**: 정상적으로 받았음을 송신 측에 알림
5. **TCP 헤더 제거**: 순수 **데이터(Payload)** 추출

**UDP의 경우:**
1. **체크섬 검증**: 데이터그램이 손상되지 않았는지 확인 (선택적)
2. **포트 번호 확인**: 목적지 포트 번호를 보고 애플리케이션 결정
3. **UDP 헤더 제거**: 순수 **데이터** 추출

## 5단계: 응용 계층(L7~L5) - 데이터 전달

추출된 순수 데이터가 애플리케이션으로 전달됩니다.

예를 들어:
- HTTP 데이터 → 웹 브라우저에 표시
- SMTP 데이터 → 이메일 클라이언트에 전달
- DNS 응답 → 도메인 이름 해석

사용자는 이 단계에서 비로소 웹페이지를 보거나, 이메일을 읽거나, 파일을 다운로드할 수 있게 됩니다.

> 문제 | 디캡슐화 과정에서 가장 먼저 제거되는 것은?

정답은 → L2의 Ethernet 트레일러(FCS)와 헤더입니다. 디캡슐화는 하위 계층(L2)에서 시작하여 상위 계층(L7)으로 올라가며 진행됩니다.

# 7. ARP의 역할

캡슐화와 디캡슐화 과정에서 **ARP(Address Resolution Protocol)** 는 매우 중요한 역할을 합니다.

## ARP란?

ARP는 **IP 주소를 MAC 주소로 변환**하는 프로토콜입니다. L3의 IP 주소는 알지만 L2의 MAC 주소를 모를 때 사용합니다.

## 송신 측에서의 ARP

캡슐화 과정에서 L2 프레임을 만들 때:
1. 목적지 IP 주소는 알고 있음 (예: 93.184.216.34)
2. 하지만 목적지 MAC 주소는 모름
3. ARP 요청을 브로드캐스트: "93.184.216.34의 MAC 주소가 뭐야?"
4. 해당 IP를 가진 장비가 응답: "내 MAC은 11:22:33:44:55:66이야"
5. 이 정보를 ARP 캐시에 저장
6. Ethernet 헤더에 목적지 MAC 주소를 넣어 프레임 완성

## 수신 측에서의 ARP

디캡슐화 과정에서 수신한 프레임의 MAC 주소를 확인:
1. 프레임의 목적지 MAC 주소가 자신의 MAC 주소와 일치하는지 확인
2. 일치하면 프레임을 처리하고 디캡슐화 계속
3. 일치하지 않으면 프레임 폐기

또한 수신 측도 나중에 응답을 보낼 때를 위해 송신 측의 IP-MAC 매핑을 ARP 캐시에 저장합니다.

## ARP 캐시 확인

Windows에서:
```bash
arp -a
```

Linux/Mac에서:
```bash
arp -n
```

출력 예시:
```
Internet Address      Physical Address      Type
192.168.1.1          11-22-33-44-55-66     dynamic
192.168.1.100        aa-bb-cc-dd-ee-ff     dynamic
```

# 8. 실무에서 자주 사용되는 프로토콜 조합

각 계층에는 다양한 프로토콜이 존재하지만, 실무에서는 특정 조합이 압도적으로 많이 사용됩니다.

## 가장 일반적인 조합

**웹 브라우징 (HTTP/HTTPS):**
- L7: HTTP / HTTPS
- L4: **TCP** (포트 80 / 443)
- L3: **IP** (IPv4 또는 IPv6)
- L2: **Ethernet** (유선) 또는 **WiFi** (무선)

**이메일 전송 (SMTP):**
- L7: SMTP
- L4: **TCP** (포트 25, 587)
- L3: **IP**
- L2: **Ethernet** / **WiFi**

**DNS 조회:**
- L7: DNS
- L4: **UDP** (포트 53, 빠른 조회용) 또는 TCP (큰 응답)
- L3: **IP**
- L2: **Ethernet** / **WiFi**

**파일 전송 (FTP):**
- L7: FTP
- L4: **TCP** (포트 20, 21)
- L3: **IP**
- L2: **Ethernet** / **WiFi**

## 왜 이 조합들이 일반적인가?

**TCP/IP + Ethernet**은 인터넷의 표준이 되었기 때문입니다:
- **IP**: 전 세계 어디든 패킷을 라우팅할 수 있는 범용성
- **TCP**: 신뢰성 있는 데이터 전송 보장 (대부분의 애플리케이션에 필요)
- **UDP**: 빠른 전송이 필요한 실시간 애플리케이션에 적합
- **Ethernet**: 유선 LAN의 사실상 표준
- **WiFi**: 무선 LAN의 사실상 표준

실무에서 네트워크 문제를 해결할 때도 이 프로토콜들을 중심으로 분석하게 됩니다.

# 9. 캡슐화와 디캡슐화의 전체 흐름

전체 과정을 하나의 예시로 정리해보겠습니다.

## 시나리오: 웹사이트 접속

**송신 측 (컴퓨터 A) - 캡슐화:**
```
1. L7: HTTP 요청 생성 "GET /index.html"
   → Data

2. L4: TCP 헤더 추가 (포트 54321 → 80)
   → [TCP Header] + [Data] = Segment

3. L3: IP 헤더 추가 (192.168.1.100 → 93.184.216.34)
   → [IP Header] + [Segment] = Packet

4. L2: Ethernet 헤더 + FCS 추가
   → [Eth Header] + [Packet] + [FCS] = Frame

5. L1: 프레임을 전기 신호로 변환하여 전송
```

**수신 측 (웹 서버) - 디캡슐화:**
```
1. L1: 전기 신호 수신, 비트로 변환

2. L2: 프레임 재구성
   - FCS 검증 (오류 없음)
   - MAC 주소 확인 (자신에게 온 프레임 맞음)
   - Ethernet 헤더와 FCS 제거
   → Packet 추출

3. L3: IP 헤더 처리
   - 체크섬 검증
   - 목적지 IP 확인 (자신의 IP 맞음)
   - IP 헤더 제거
   → Segment 추출

4. L4: TCP 세그먼트 처리
   - 체크섬 검증
   - 포트 80 확인 (웹 서버)
   - TCP 헤더 제거
   → Data 추출

5. L7: HTTP 요청 처리
   - 웹 서버가 요청을 받아 처리
   - /index.html 파일 읽기
   - HTTP 응답 생성 (역방향 캡슐화 시작)
```

이렇게 송신 측에서 캡슐화하고, 수신 측에서 디캡슐화하는 과정을 거쳐 데이터가 전달됩니다.

# 10. 마치며

캡슐화와 디캡슐화는 네트워크 통신의 근본적인 메커니즘입니다. 겉으로는 단순히 데이터가 전송되는 것처럼 보이지만, 그 내부에서는 각 계층이 협력하여 정보를 추가하고 제거하며 데이터를 목적지까지 안전하게 전달합니다.

핵심을 정리하면:

**캡슐화 (송신 측):**
- 상위 계층에서 하위 계층으로 내려가며 헤더 추가
- L7 → L4 → L3 → L2 → L1
- Data → Segment → Packet → Frame → Bit

**디캡슐화 (수신 측):**
- 하위 계층에서 상위 계층으로 올라가며 헤더 제거
- L1 → L2 → L3 → L4 → L7
- Bit → Frame → Packet → Segment → Data

**각 계층의 역할:**
- **L4**: 포트 번호로 애플리케이션 식별, 신뢰성 제어
- **L3**: IP 주소로 목적지 식별, 라우팅
- **L2**: MAC 주소로 직접 연결된 장비 식별, 오류 검출
- **L1**: 물리적 신호로 변환하여 전송

**ARP의 역할:**
- IP 주소를 MAC 주소로 변환
- L2 프레임을 만들 때 필수적

이 개념을 이해하면 네트워크 문제를 해결할 때 어느 계층에서 문제가 발생했는지 파악할 수 있고, Wireshark 같은 패킷 분석 도구를 사용할 때도 각 계층의 헤더 정보를 정확히 이해할 수 있습니다. 네트워크 엔지니어로 성장하기 위한 필수적인 지식이니 반드시 숙지하시기 바랍니다.
